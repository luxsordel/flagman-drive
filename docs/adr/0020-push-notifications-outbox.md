# ADR-0020. Push-уведомления: порт, Expo Push Service и очередь в Postgres (outbox)

- Статус: принято
- Дата: 2026-10-27

## Контекст
Задача #119 вводит push-уведомления клиенту: бронь скоро истечёт и истекла, низкий заряд в поездке, поездка
завершена, оплата не прошла. Дальше на них построятся чат поддержки (#120) и штрафы (#121).
Требования из задачи и `docs/03-security.md`:
- внешний сервис доставки — только через порт в `ports.py`, для разработки и тестов нужен фейковый провайдер;
- текст собирается на сервере на языке клиента, клиент присылает только push-токен;
- ошибка доставки не ломает бизнес-операцию; повторы с ограничением попыток;
- одно и то же событие не приходит дважды;
- push-токен и персональные данные не логируются, чужие устройства недоступны.

Отправка идёт по событию, а очереди заданий в проекте нет: в ADR-0013 arq отклонили из-за несовместимости
с `redis>=6` и договорились выбрать инструмент, когда понадобятся задания по событию.

## Решение
- **Провайдер — Expo Push Service.** Приложение уже на Expo (ADR-0001, ADR-0016): один HTTPS API для APNs
  и FCM, без своих ключей APNs и FCM в API. Порт `PushProvider` (`notifications/ports.py`): «отправь пачку
  сообщений, верни статус каждого». Адаптеры:
  - `ExpoPushProvider` — `POST https://exp.host/--/api/v2/push/send` пачками по 100. Ответ по сообщению:
    `ok`, `DeviceNotRegistered` (токен удаляется) или другая ошибка (сообщение не повторяется). Отказ всего
    запроса (сеть, 401, 429, 5xx, нечитаемый ответ) — `PushProviderError`, вся пачка повторяется позже.
    `EXPO_ACCESS_TOKEN` нужен, только если в проекте Expo включена «enhanced push security»;
  - `FakePushProvider` — для разработки и тестов: ничего не доставляет, пишет в лог только тип события.
  - Выбор — `NOTIFICATIONS_PROVIDER` (`expo`, `fake` или пусто). `fake` при `API_ENV=prod` запрещён.
    Пусто — уведомления копятся в очереди и уходят, когда провайдер настроят.
- **Очередь — таблица `notification_outbox` в Postgres (transactional outbox), без новых зависимостей.**
  - Модуль вызывает `notifications.service.notify_client(db, user_id, notification, now)` **в своей
    транзакции**. Уведомление сохраняется вместе с изменением, о котором сообщает, или не сохраняется
    вовсе: откат брони не оставит уведомления «бронь истекла».
  - Дедупликация — уникальный `dedup_key` = `<событие>:<rental_id>`, вставка `ON CONFLICT DO NOTHING`.
    Вызывающий может сообщать о событии сколько угодно раз — например, о низком заряде на каждой телеметрии.
  - Отключённая клиентом категория проверяется при постановке: такое уведомление в очередь не попадает.
  - Отправляет `flagman-worker` задачей `notifications_dispatch` раз в
    `NOTIFICATIONS_DISPATCH_INTERVAL_SECONDS` (по умолчанию 5 с), под своим advisory lock, как в ADR-0013.
    Строки забираются в одной транзакции (`FOR UPDATE SKIP LOCKED`, `attempts + 1`, `next_attempt_at`
    сдвигается на 2 минуты как «аренда»), провайдер вызывается вне транзакции, итог пишется во второй.
    Если воркер упал между ними, строка снова станет доступна через 2 минуты: доставка «хотя бы один раз».
  - Повторы после отказа провайдера: через 30 с, 1, 2 и 4 минуты; после 5 попыток — `undelivered`.
  - Отправленные и недоставленные строки хранятся `NOTIFICATIONS_RETENTION_DAYS` (30 дней) и удаляются
    часовой задачей `outbox_cleanup`.
- **Шаблоны и язык.** Шаблоны ru/en в `notifications/domain.py`. Язык — из профиля клиента (`users.language`)
  в момент отправки. В `params` уведомления только числа (минуты, проценты, копейки), без имён, телефонов
  и мест. В `data` push-сообщения — тип события и `rental_id` для перехода на экран.
- **Устройства.** Таблица `push_devices`: одно устройство на сессию входа (`session_id` уникален, FK на
  `auth_sessions` с каскадом), токен уникален.
  - `PUT /me/push-device` регистрирует токен для текущей сессии, `DELETE /me/push-device` удаляет. Устройство
    находится по сессии из access-токена, поэтому id чужого устройства передать нельзя.
  - Токен принадлежит телефону, а не аккаунту: если на телефоне вошёл другой клиент, токен переходит к его
    сессии.
  - При отправке воркер спрашивает у `identity.service.get_active_client_sessions`, какие сессии живы.
    Устройства вышедших и отозванных сессий удаляются и ничего не получают. Выход из аккаунта прекращает
    push сразу, даже если приложение не успело вызвать `DELETE`.
- **Настройки клиента.** `GET/PATCH /me/notification-preferences`, категории `reservation`, `trip`, `payment`.
  `trip` и `payment` обязательные, отключить их нельзя (422 `notification-category-mandatory`). Хранятся
  только отключённые категории (`notification_opt_outs`).

## Альтернативы
- **Отправлять сразу из запроса API.** Ошибка или медленный Expo задерживали бы бизнес-операцию, а
  уведомление из откатившейся транзакции всё равно ушло бы. Повторы пришлось бы делать отдельно.
- **taskiq + taskiq-redis или arq.** Настоящая очередь, но две новые зависимости (arq ещё и несовместим
  с нашим `redis`, ADR-0013). Задание в Redis не атомарно с транзакцией Postgres: нужен тот же outbox.
- **Свои ключи APNs и FCM напрямую.** Два протокола и два набора секретов вместо одного API. Для пилота
  на Expo смысла нет; порт позволяет поменять провайдера позже.
- **Проверять отключённые категории при отправке, а не при постановке.** Тогда очередь копила бы
  уведомления, которые никто не получит. Включение категории назад к уже прошедшим событиям не относится.

## Последствия
- Модули сообщают о событиях одной функцией в своей транзакции; провайдер и повторы их не касаются.
- Задержка доставки — до интервала опроса (5 с) плюс время Expo. Для брони и поездки достаточно.
- Доставка «хотя бы один раз»: при падении воркера посреди отправки уведомление может прийти дважды.
- Квитанции Expo (receipts) пока не опрашиваются. `DeviceNotRegistered`, пришедший только в квитанции,
  удалит токен при следующей отправке на него, а не сразу.
- В вебе push нет; в приложении это объясняется на экране настроек.
- Для реальных устройств нужны проект EAS (`projectId`) и ключи FCM для Android в EAS — это настройка
  сборок (#123), в коде API ничего не меняется.
- ADR-0013 дополняется: у задач воркера теперь свои интервалы (часовые чистки и частая отправка).
