# ADR-0006. Единый формат ошибок API — RFC 9457 (Problem Details)

- Статус: принято
- Дата: 2026-10-22

## Контекст
Все клиенты (мобильное приложение, веб, админка) получают типы из сгенерированного по OpenAPI клиента
(`packages/api-client`). Чтобы обработка ошибок на фронте была одинаковой, нужен один формат для всех
ошибок бэкенда: бизнес-ошибок, ошибок валидации, 404/405 и необработанных исключений. При этом ответ
не должен раскрывать внутренности сервера и не должен возвращать клиенту его же персональные данные.

## Решение
Все ошибки отдаются как **RFC 9457 Problem Details**, `Content-Type: application/problem+json`:

```json
{
  "type": "urn:flagman:problem:car-not-found",
  "title": "Car not found",
  "status": 404,
  "detail": "No car with this id.",
  "request_id": "6f1c…",
  "errors": [{"loc": ["body", "phone"], "message": "…", "type": "string_pattern_mismatch"}]
}
```

- `type` — стабильный машиночитаемый код: `urn:flagman:problem:<slug>` для наших ошибок,
  `about:blank` для обычных HTTP-статусов (тогда `title` — стандартная фраза статуса).
  Клиенты ветвятся по `type`, а не по тексту.
- `title` — краткое описание на английском, одинаковое для всех ошибок этого типа. Тексты для
  пользователя клиенты берут из своих i18n-словарей по `type`.
- Расширения: `request_id` (тот же, что в заголовке `X-Request-ID` и в логах) и `errors` для ошибок валидации.
- В `errors` только место, сообщение и тип ошибки, **без введённого значения** — оно может быть телефоном
  или номером документа. Сообщение отдаётся только для встроенных ошибок pydantic: почти все они —
  шаблоны по схеме («Input should be a valid integer») или фиксированные тексты парсеров. Исключения,
  для которых вместо текста всегда `"Invalid value"`:
  - `value_error`, `assertion_error` и собственные типы (`PydanticCustomError`) — текст пишет наш
    валидатор, и в нём легко оказывается значение;
  - `union_tag_invalid` — pydantic цитирует присланный тег размеченного объединения;
  - `get_attribute_error`, `iteration_error`, `mapping_type`, `datetime_object_invalid` — в текст
    подставляется сообщение произвольного исключения.

  Список — `_SAFE_MESSAGE_TYPES` в `flagman/core/errors.py`. Причину такой ошибки клиент различает
  по `type`: для своих проверок используйте `PydanticCustomError` с понятным типом, например
  `phone_invalid`.
- Ответ 500 содержит только `type`, `title`, `status`, `request_id`; подробности — только в логах.
- Бизнес-ошибки — подклассы `flagman.core.errors.AppError` с полями `status`, `slug`, `title`.
- В OpenAPI схема `Problem` описана под `application/problem+json` для 422 и 500 на всех эндпоинтах.

## Альтернативы
- **Формат FastAPI по умолчанию** (`{"detail": ...}`) — разная форма у разных ошибок, у 422 в ответе
  есть введённое значение (`input`), нет кода ошибки для ветвления.
- **Свой формат** (`{"error": {"code", "message"}}`) — то же самое, но без стандарта: больше объяснять,
  нет поддержки в библиотеках.

## Последствия
- Клиенты пишут один обработчик ошибок для всех запросов.
- Новый тип ошибки = новый подкласс `AppError` и строка в i18n клиентов.
- `type` нельзя переименовывать после релиза — клиенты на него опираются.
