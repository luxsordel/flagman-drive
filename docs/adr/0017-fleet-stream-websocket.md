# ADR-0017. Живой парк для сотрудников: WebSocket и уведомления Postgres

- Статус: принято
- Дата: 2026-10-26

## Контекст
Раздел «Парк» в админке (#96) должен показывать машины в реальном времени: телеметрия приходит
каждые несколько секунд, статус меняется по переходам парка (а с этапа 3 — аренды), результаты ручных
команд должны видеть все сотрудники на смене. Опрашивать список раз в несколько секунд дорого и медленно,
поэтому нужен поток изменений от сервера.

Ограничения:
- API работает в нескольких процессах: изменение, принятое одним процессом, должно дойти до сокетов,
  которые держат другие;
- браузер не умеет передавать заголовки в WebSocket, а токен в URL оседает в логах прокси и в истории;
- сокет живёт дольше 15-минутного токена доступа, а отзыв сессии и отключение сотрудника должны
  закрывать его без ожидания;
- медленный сотрудник (плохая сеть, спящая вкладка) не должен тормозить остальных.

## Решение

### Рассылка между процессами — `LISTEN/NOTIFY` Postgres
- Модуль `fleet` в той же транзакции, что и изменение, вызывает `pg_notify('fleet_changes', ...)`
  (`fleet/changes.py`, `repository.notify`). Postgres отправляет уведомления **только после коммита**,
  поэтому откатанное изменение до сотрудников не доходит. Изменение статуса из чужой транзакции
  (аренда на этапе 3) тоже даёт уведомление без отдельного кода в `rentals`.
- В уведомлении только id машин, до 150 штук (лимит Postgres 8000 байт). Пакет телеметрии из 1000 машин
  даёт 7 уведомлений, а не 1000.
- Каждый процесс API держит одно отдельное соединение `asyncpg` с `LISTEN fleet_changes` (`FleetHub`
  в `fleet/stream.py`), склеивает накопившиеся уведомления, **сам читает** состояние этих машин из БД
  и рассылает его своим сокетам одним сообщением. Читать после коммита надёжнее, чем передавать
  состояние в уведомлении: процесс никогда не пришлёт состояние старее, чем в БД.
- Соединение проверяется `SELECT 1` раз в 30 с. Потеряно соединение — процесс мог пропустить
  уведомления, поэтому закрывает все свои сокеты кодом 1013 и переподключается. Пока он не слушает,
  новые сокеты тоже получают 1013.

### Протокол
Эндпоинт `GET /admin/fleet/stream` (WebSocket). Сообщения — JSON-текст.

1. Сервер проверяет заголовок `Origin` по `API_CORS_ORIGINS`. На сокеты CORS не действует, а без проверки
   любой сайт, открытый у сотрудника, мог бы подключиться из его браузера. Нет `Origin` или он чужой —
   сервер принимает соединение и сразу закрывает его кодом 1008. Отказ на рукопожатии браузер видит
   как 1006, то есть как обрыв, и переподключался бы бесконечно. До сообщения `auth` сервер ничего
   не отправляет, так что чужая страница получает только закрытие.
2. Первое сообщение клиента — `{"type": "auth", "token": "<access token сотрудника>"}`, не позже 10 с.
   Проверяются подпись и срок токена, роль (`operator`, `technician`, `admin`) и то, что сессия
   в БД жива и сотрудник не отключён.
3. Сервер отвечает полным снимком: `{"type": "snapshot", "items": [...], "rules": {...}, "as_of": "..."}`,
   тот же формат, что `GET /admin/fleet/cars`. Подписка оформляется **до** чтения снимка, поэтому изменения
   между ними не теряются. Если изменение пришло дважды (в снимке и следом сообщением), повтор безвреден:
   каждое сообщение — полное состояние машины.
4. Дальше сервер шлёт:
   - `{"type": "cars", "items": [...], "as_of": "..."}` — машины, которые изменились (телеметрия, статус,
     ответ на команду);
   - `{"type": "command", "command": {...}}` — результат ручной команды любого сотрудника: кто, какой
     машине, что и чем кончилось.
5. Клиент продлевает доступ тем же сообщением `auth` с новым токеном, пока старый не истёк. Токен другого
   сотрудника — закрытие 1008.
6. Свежесть телеметрии сервер не присылает: она меняется со временем без событий. Клиент считает её сам
   по `rules.telemetry_max_age_seconds` от `as_of` (часы сервера, а не браузера).

Коды закрытия:

| Код | Когда | Что делает клиент |
|---|---|---|
| 4401 | нет токена за 10 с, токен неверный или истёк, сессия отозвана или сотрудник отключён | обновляет токен и переподключается; не вышло — экран входа |
| 4403 | роль без доступа к парку | не переподключается |
| 1008 | чужой `Origin`, неверное или бинарное сообщение, токен другого сотрудника | не переподключается (ошибка клиента) |
| 1013 | сокет отстал, процесс потерял связь с Postgres или ещё не слушает | переподключается с паузой, получает снимок |
| 1001 | сервер останавливается | переподключается с паузой |

### Безопасность
- Токен не попадает в URL и в логи: в логах только `staff_id` и код закрытия.
- Сессия проверяется в БД при входе, при каждом продлении и раз в 30 с. Отозванная сессия теряет поток
  не позже чем через 30 с, а не через 15 минут, как обычные запросы с тем же токеном. Проверка токена,
  роли и сессии — общая функция `identity.service.authenticate_staff`.
- Сообщение клиента длиннее 4096 символов — закрытие 1008.

### Медленные подписчики
У каждого сокета своя очередь на 64 сообщения. Рассылка кладёт в очередь без ожидания: если очередь полна,
сокет закрывается кодом 1013, клиент переподключается и получает свежий снимок. Остальные сокеты этого
не замечают. При телеметрии раз в 5 с это минуты отставания.

## Альтернативы
- **Redis pub/sub.** Redis уже есть, но публикация в Redis не транзакционна: публиковать до коммита —
  сотрудники увидят откатанное изменение, после коммита — изменение может потеряться, если процесс упадёт
  между коммитом и публикацией. Для смены статуса из чужой транзакции (аренды) пришлось бы ещё и цеплять
  хуки к сессии SQLAlchemy. `NOTIFY` даёт транзакционность бесплатно.
- **Опрос `GET /admin/fleet/cars` раз в несколько секунд.** Просто, но при 1000 машин это сотни КБ
  на каждого сотрудника каждые несколько секунд и задержка до интервала опроса.
- **Server-Sent Events.** Односторонний поток проще, но `EventSource` не умеет заголовки, токен ушёл бы
  в URL, а продлевать токен пришлось бы переподключением.
- **Токен в query string или в `Sec-WebSocket-Protocol`.** Query string пишут логи прокси. Подпротокол
  формально не для этого и тоже часто логируется.
- **Сжимать очередь медленного сокета** (держать только последнее состояние каждой машины). Отстающий
  сокет никогда не закрывался бы, но кода больше, а выигрыш для пилота с несколькими сотрудниками
  не нужен.

## Последствия
- Любое изменение машины в `fleet` должно идти через сервис, который вызывает `repository.notify`.
  Прямой `UPDATE cars` мимо сервиса до сотрудников не дойдёт.
- Каждый процесс API держит одно лишнее соединение с Postgres вне пула.
- Коммиты с `NOTIFY` выстраиваются в очередь на общей блокировке Postgres. При телеметрии раз в 5 с это
  незаметно; если изменений станет на порядки больше, придётся пересмотреть (например, отдельный процесс
  рассылки).
- Сообщения потока не входят в OpenAPI: их типы в админке описаны вручную (`apps/admin/src/fleet/`),
  а элементы `items` — это `StaffCarOut` из сгенерированного клиента.
- Dev-сервер админки проксирует WebSocket на API (`ws: true` в `vite.config.ts`), а `API_CORS_ORIGINS`
  должен содержать адрес админки.
