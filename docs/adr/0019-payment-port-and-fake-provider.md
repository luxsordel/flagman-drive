# ADR-0019. Порт платежей и тестовый провайдер `FakeProvider`

- Статус: принято
- Дата: 2026-10-26

## Контекст
Задача #109 вводит привязку карты, а задача #111 — холд при старте поездки и списание по её итогам. В пилоте
денег нет (`docs/01-vision-and-mvp.md`): реальный провайдер (bePaid или аналог из РБ) подключится позже.
Требования из `docs/02-architecture.md` и `docs/03-security.md`:
- внешний провайдер — только через интерфейс в `ports.py`, замена провайдера не трогает домен;
- номер карты не проходит через наши эндпоинты и не хранится;
- вебхуки платёжки подписаны HMAC с меткой времени, повтор безопасен;
- платёжные операции идемпотентны (`Idempotency-Key`), у каждой — статус и журнал попыток;
- клиент видит только свои карты.

## Решение

### Порт `PaymentProvider` (`payments/ports.py`)
- `start_card_binding` возвращает адрес страницы провайдера. Клиент вводит карту там, а не у нас.
- `parse_webhook` сначала проверяет подпись (`WebhookSignatureInvalidError`), потом читает тело.
- Операции: `hold`, `capture`, `charge` (сверх холда или долг), `void`, `refund`. В каждую передаётся
  ключ идемпотентности. Неизвестный исход (таймаут, обрыв) — `PaymentProviderError`.
- Адаптер реального провайдера — своя реализация порта со своей страницей, подписью и форматом тела.
  Остальной модуль не меняется.

### Привязка карты
1. `POST /payment-cards/bindings` с `return_url` создаёт привязку `pending` на 30 минут и возвращает адрес
   страницы провайдера. Rate limit — 10 привязок в час на клиента.
2. Клиент вводит карту на странице провайдера. Провайдер шлёт вебхук с итогом, затем возвращает клиента
   на `return_url?binding_id=…`.
3. Приложение спрашивает `GET /payment-cards/bindings/{id}`, пока статус `pending`. Итог: `succeeded` (с
   картой), `declined`, `cancelled` или `expired`.

`return_url` — только наша схема `flagmandrive://`, `exp://` Expo Go вне прода или страница с origin из
`API_CORS_ORIGINS`. Иначе ссылка на страницу карты уводила бы клиента на чужой сайт.

### Что храним о карте
- Платёжную систему, последние 4 цифры, срок действия, признак «основная».
- Токен провайдера: AES-256-GCM с ключом `PAYMENTS_TOKEN_ENCRYPTION_KEY`, id карты — связанные данные
  (шифртекст, скопированный в другую строку, не расшифруется). Дамп базы без ключа не даёт списать деньги.
- Токен не отдаётся клиенту и не пишется в логи. Удалённая карта теряет токен (`removed_at`, токен `NULL`),
  а строка остаётся: на неё ссылаются операции.
- Основная карта у клиента одна (частичный уникальный индекс). Первая привязанная становится основной.
  При удалении основной её место занимает самая новая из оставшихся.

### Вебхуки
- `POST /payments/webhooks/fake`, вне OpenAPI: его зовёт провайдер, а не клиенты.
- Формат подписи `FakeProvider` — как у телематики ([ADR-0007](0007-telematics-hmac-signing.md)):
  `X-Flagman-Timestamp` и `X-Flagman-Signature`, окно ±300 с (`PAYMENTS_WEBHOOK_TOLERANCE_SECONDS`).
  Код подписи берётся из `fleet.signing`, а не копируется. Секрет свой — `PAYMENTS_WEBHOOK_SECRET`.
- Повтор безопасен: id события пишется в `payment_webhook_events`, повтор отвечает `200 {"applied": false}`
  и ничего не меняет. Привязка завершается один раз: позднее событие для завершённой привязки игнорируется.

### Операции (для `rentals`)
- `payments.service.hold / capture / charge / void / refund`. Вызывающий передаёт ключ идемпотентности;
  ключ уникален в `payment_operations` и уходит провайдеру как есть.
- Повтор с тем же ключом возвращает ту же операцию. Провайдера зовут снова, только если исход
  неизвестен (`pending` или `failed`). Тот же ключ с другими параметрами — `409 idempotency-key-reused`.
- Каждый вызов провайдера пишется в `payment_attempts`: статус и вид ошибки, без ответа провайдера.
- Правила в домене: захват — не больше холда и один раз, отмена холда — один раз, возврат — не больше
  взятого за вычетом прежних возвратов. Строка родительской операции блокируется, поэтому два параллельных
  захвата одного холда не проходят оба.
- Транзакция не держится открытой во время сетевого вызова: операция записывается `pending`, после
  ответа провайдера — итог. Поэтому функции `payments.service` открывают свои транзакции, а не
  присоединяются к транзакции вызывающего.

### `FakeProvider`
- Живёт внутри API (`payments/fake_provider.py`, страница — `payments/fake_pages.py`). Своих таблиц нет:
  - сессия страницы подписана HMAC и содержит id привязки, `return_url` и срок;
  - токен карты говорит, как карта себя ведёт.
- Тестовые карты (любой будущий срок и CVC):
  - `4242 4242 4242 4242` (Visa) и `5555 5555 5555 4444` (Mastercard) — успех;
  - `4000 0000 0000 9995` — привязывается, но холд и списание отклоняются: `insufficient_funds`;
  - `4000 0000 0000 0002` и любая другая — привязка отклонена.
- Номер читается только на странице, чтобы выбрать поведение. Дальше уходят только последние 4 цифры.
- Вебхук `FakeProvider` передаёт в тот же код, что принимает HTTP-вебхук, но в процессе, без сетевого
  вызова: проверка подписи работает так же. HTTP-эндпоинт вебхука тоже есть, его проверяют тесты.
- У страницы свой CSP, такой же узкий: стиль по хэшу, `form-action` — только сам API и адрес возврата.
  `SecurityHeadersMiddleware` больше не перезаписывает CSP, который задал маршрут.
- Без `PAYMENTS_PROVIDER` API работает, а привязка карт и страница отвечают `503 payments-unavailable`.

## Альтернативы
- **Ввод карты в нашем приложении и передача номера провайдеру через API.** Номер прошёл бы через наши
  эндпоинты и логи, и API попал бы под PCI DSS в полном объёме. Страница провайдера это исключает.
- **`FakeProvider` отдельным сервисом, как эмулятор машин.** Честнее по сети, но ещё один контейнер,
  секрет и адрес ради заглушки. Поведение порта от этого не меняется.
- **Хранить токен открытым текстом.** Токен — не номер карты, но с ним и ключом магазина провайдер
  спишет деньги. Шифрование стоит одной настройки.
- **Транзакция вызывающего на всю операцию.** Проще для `rentals`, но держит блокировки на время сетевого
  вызова, а при откате теряет запись о деньгах, которые провайдер уже взял.

## Последствия
- `rentals` (#110, #111) вызывает `payments.service`, сохраняет id операций в своих строках и повторяет
  вызов с тем же ключом, если не знает исход. Фоновый повтор списаний (#111) использует `failed`-операции.
- Подключение bePaid — новый адаптер порта, его вебхук и настройки. Нужно решить, где хранить его
  идентификатор магазина, и добавить проверку IP вебхуков, если провайдер её даёт.
- Код подписи из `fleet.signing` стоит перенести в `core`, когда им начнёт пользоваться третий модуль.
