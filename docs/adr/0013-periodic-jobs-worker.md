# ADR-0013. Периодические задачи: свой процесс `flagman-worker` вместо arq

- Статус: принято
- Дата: 2026-10-24 (обновлено 2026-10-25: повтор в закончившейся сессии, #82)

## Контекст
Первая фоновая задача в проекте — чистка данных входа (#46):
- истёкшие коды в `pending_otps`;
- сессии клиентов и сотрудников, закончившиеся больше N дней назад, вместе с их refresh-токенами (ADR-0009, ADR-0011).

Задача периодическая, раз в час. Очередь заданий ей не нужна.

В `docs/02-architecture.md` для фоновых задач был выбран **arq**. Но последняя версия arq (0.28.0, апрель 2026) требует `redis>=4.2,<6`, и в основной ветке у них то же ограничение. API использует `redis>=8.1`, а два разных клиента Redis в одном окружении uv не поставит. Откатывать основную библиотеку ради планировщика мы не хотим.

## Решение
- **Свой небольшой процесс `flagman-worker`** (`apps/api/src/flagman/worker.py`), без новых зависимостей.
  - При старте сразу выполняет задачи, потом повторяет их раз в час (`JOB_INTERVAL`).
  - Ошибка одного запуска пишется в лог `auth_cleanup_failed` и не останавливает процесс. Например, Postgres перезапускается или на новой базе ещё не применены миграции. После ошибки следующий запуск через минуту (`RETRY_AFTER`), а не через час: иначе после `alembic upgrade head` чистка ждала бы до часа.
  - Останавливается по SIGTERM (так останавливает контейнеры Docker) и по Ctrl+C, не дожидаясь следующего запуска.
- **Одновременно задачу выполняет только одна копия.** Перед запуском worker берёт advisory lock в Postgres (`pg_try_advisory_lock`) на отдельном соединении.
  - Блокировка на уровне соединения, а не транзакции: чистка коммитит каждую пачку, и блокировка транзакции снялась бы после первой.
  - Если блокировку держит другая копия, запуск пропускается (`auth_cleanup_skipped`).
  - Если процесс умер, Postgres закрывает соединение и снимает блокировку сам.
  - У каждой задачи свой номер блокировки (`AUTH_CLEANUP_LOCK`).
- **Worker не получает секретов API.** Он читает только `WorkerSettings`: подключение к Postgres, уровень логов и `AUTH_CLEANUP_RETENTION_DAYS`. JWT-секрет, pepper, ключ TOTP, Redis и S3 ему не нужны и в его контейнер не передаются.
- **Сервис `worker` в `infra/docker-compose.yml`.** Тот же образ, что у API (`flagman-api:local`, один `build` и один тег у обоих сервисов, поэтому пересобирать их нужно вместе: `up -d --build api worker`), команда `flagman-worker`, те же ограничения: файловая система только для чтения, `cap_drop: ALL`, `no-new-privileges`.
  - HTTP-порта у worker нет, поэтому `HEALTHCHECK` образа (он проверяет порт API) для него выключен.
  - Упавший процесс перезапускает `restart: unless-stopped`.
- **Чистка данных входа** (`identity.service.clean_up_auth_data`):
  - удаляет пачками по 1000 строк, каждая пачка в своей транзакции, с `FOR UPDATE SKIP LOCKED`. Строку, которую прямо сейчас держит обновление токена или проверка кода, чистка пропускает до следующего запуска;
  - обновление токена блокирует строку токена, потом сессии, а чистка — сессию, потом каскадом её токены. Если они встретятся (повтор старого токена закончившейся сессии во время чистки), получится deadlock. Поэтому транзакция чистки ждёт блокировку не дольше 100 мс (`lock_timeout`, меньше `deadlock_timeout` Postgres в 1 с): сдаётся чистка, а обновление токена не падает с 500. Сдавшаяся категория (коды, сессии клиентов, сессии сотрудников) пишет `auth_cleanup_lock_timeout` и ждёт следующего запуска, остальные чистятся дальше;
  - удаляет только истёкшие коды и только закончившиеся сессии. Живая сессия не удаляется, даже если её использованным токенам много дней: по ним распознаётся повторное использование (ADR-0009);
  - срок хранения закончившихся сессий — `AUTH_CLEANUP_RETENTION_DAYS`, по умолчанию 7 дней;
  - в лог пишет только количества удалённого.

## Альтернативы
- **arq** — несовместим с `redis>=6`, см. «Контекст».
- **Откатить `redis` до 5.x ради arq** — основная библиотека API уходит на устаревшую ветку ради одной задачи раз в час.
- **saq** — с Redis ограничивает `redis<8`. Есть бэкенд на Postgres (`saq[postgres]`), но он работает через psycopg: второй драйвер Postgres рядом с asyncpg ради одной задачи.
- **taskiq + taskiq-redis и его планировщик** — настоящая очередь сразу, но две новые зависимости и брокер ради одной периодической задачи.
- **APScheduler** — версия 3 не рассчитана на asyncio изначально, версия 4 так и не вышла из предварительных.
- **Цикл внутри процесса API (lifespan)** — без нового контейнера, но задача запускалась бы в каждой копии API и останавливалась бы с ним; API пришлось бы делить ресурсы с чисткой.
- **cron в контейнере или на хосте** — ещё один инструмент в образе. Расписание жило бы вне кода, и его было бы труднее тестировать.

## Последствия
- Следующая периодическая задача — ещё одна функция в `worker.py` со своим номером блокировки.
- **Очереди заданий по-прежнему нет.** Когда понадобятся задания по событию (таймауты броней, повторы платежей, уведомления), выберем инструмент заново: arq, если он снимет ограничение на `redis`, или taskiq. Это решение тогда заменит новый ADR.
- Запуск идёт раз в час от старта процесса, а не по часам: точное время запуска чистке неважно.
- Срок хранения закончившихся сессий на безопасность не влияет: их использованные токены ничего не отзывают и до чистки (#82, ADR-0009).
- Упавший запуск видно только в логах: метрик и оповещений пока нет.
