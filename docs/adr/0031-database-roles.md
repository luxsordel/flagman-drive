# ADR-0031. Роли базы данных: суперпользователь, владелец схемы, приложение

- Статус: принято
- Дата: 2026-11-10

## Контекст
API, воркер, миграции, сиды и тесты ходили в Postgres одной ролью: суперпользователем из образа (`POSTGRES_USER`).
Взлом API давал полные права на БД. В том числе можно было снять триггеры журнала аудита и подделать
`occurred_at`: ADR-0010 прямо называет отдельные роли единственной защитой от этого. Находка #162,
`docs/10-security-review.md`, задача #167.

Ограничения: стенд и локальные стенды разработчиков уже существуют, и у их томов роль одна. Роли нельзя создавать
миграцией без права CREATEROLE и без паролей в коде. Стенд выкладывает старые образы вместе с `infra/` их коммита
(ADR-0021).

## Решение
- **Три роли с разными паролями:**
  - `POSTGRES_SUPERUSER` — суперпользователь образа. Только создаёт роли, делает копии и восстанавливает базу
    (`DROP` и `CREATE DATABASE`).
  - `POSTGRES_OWNER_USER` — владелец схемы `public` и всех таблиц. Только запускает миграции. Без SUPERUSER,
    CREATEDB, CREATEROLE, REPLICATION и BYPASSRLS.
  - `POSTGRES_USER` — вход API, воркера и сидов. Член групповой роли `flagman_app` (NOLOGIN) с фиксированным
    именем, на неё миграции и выдают права.
- **Роли создаёт `infra/postgres/bootstrap-roles.sh`**, а не миграция. Скрипт запускает суперпользователь
  через локальный сокет, и он идемпотентный. В новом томе он запускается сам из `docker-entrypoint-initdb.d`.
  В существующем его запускает `deploy.sh` перед миграциями, `restore.sh` после `pg_restore --no-owner` и
  разработчик один раз (docs/06). Каждый запуск заново выставляет атрибуты и пароли и возвращает владельцу
  таблицы, функции и типы схемы, кроме объектов расширений (PostGIS). Пароли он читает из окружения через
  `\getenv`, а не из аргументов.
- **Права на таблицы выдают миграции.** Миграция `af60e487a348`, которую запускает владелец, делает три вещи:
  - даёт `flagman_app` `SELECT, INSERT, UPDATE, DELETE` на таблицы и `USAGE, SELECT` на последовательности;
  - задаёт default privileges владельца, так что таблицы следующих миграций открыты приложению без своих `GRANT`;
  - отзывает `UPDATE, DELETE, TRUNCATE` на журналах (`audit_events`, `rental_receipts`, `rental_receipt_lines`,
    `rental_adjustments`, `client_block_events`) и всё на `alembic_version`.

  Триггеры журналов остаются вторым рубежом и защищают от владельца.
- **Отдельный сервис `migrate`** (тот же образ, профиль `tools`) получает только настройки БД и пароль
  владельца. `migrations/env.py` читает `POSTGRES_OWNER_USER` и `POSTGRES_OWNER_PASSWORD` (`MigrationSettings`) и
  отказывается работать под суперпользователем: тот стал бы владельцем новых таблиц, и default privileges к ним
  не применились бы.
- Имя `POSTGRES_USER` остаётся у роли приложения: код конфигурации API, воркера и LISTEN флота не меняется.
- Интеграционные тесты поднимают те же три роли тем же скриптом и работают ролью приложения. Запрос, на который
  у API нет прав, падает и в тестах. `tests/test_db_roles.py` проверяет:
  - отказ в изменении журналов;
  - запрет DDL;
  - права на все остальные таблицы;
  - default privileges;
  - что ни одна роль, под которой входят, не привилегирована;
  - что журнал с триггером `<таблица>_no_update_delete` без своего `REVOKE` обнаруживается.

## Альтернативы
- **Роли в миграции Alembic.** Владельцу понадобился бы CREATEROLE, то есть почти суперпользователь, а пароли
  попали бы в код или в окружение миграции. Отказались.
- **Только скрипт в `initdb.d`.** Срабатывает только на пустом томе: существующие стенды и тома разработчиков
  остались бы с одной ролью, а после `pg_restore --no-owner` таблицы снова принадлежали бы суперпользователю.
- **Права на таблицы в скрипте bootstrap** (`GRANT ... ON ALL TABLES`). Повторный запуск снова выдал бы `UPDATE`
  на журналы. Правило «какие права у какой таблицы» должно жить рядом со схемой, в миграциях.
- **Одна роль приложения, которая владеет схемой, но без суперпользователя.** Взломанный API всё равно смог бы
  снять триггеры журнала (`DROP TRIGGER` доступен владельцу), то есть главная угроза ADR-0010 осталась бы.
- **Row-level security для журналов.** Те же гарантии дают обычные права на таблицу, но RLS сложнее. Нужна только
  запрещённая операция целиком, фильтровать строки не требуется.

## Последствия
- Взлом API даёт только чтение и запись строк приложения: ни схемы, ни журналов, ни `alembic_version`, ни ролей.
- В `.env` и `stand.env` три пары «роль/пароль» вместо одной. Существующие `.env` и `stand.env` надо перевести
  один раз: `POSTGRES_USER` → `POSTGRES_SUPERUSER`, `POSTGRES_PASSWORD` → `POSTGRES_SUPERUSER_PASSWORD`, плюс
  новые строки (docs/06, docs/08). Compose без них не стартует.
- Миграции запускаются только как `run --rm migrate` или `uv run alembic` с `POSTGRES_OWNER_*` в `.env`.
- Новый неизменяемый журнал должен отозвать `UPDATE, DELETE, TRUNCATE` в своей миграции. Иначе тест упадёт.
- Откат стенда на тег до #167 автоматически не работает: старый `deploy.sh` запускает миграции ролью приложения.
  Только вручную (docs/08, «Откат»).
- Копия базы делается суперпользователем, после восстановления `restore.sh` возвращает таблицы владельцу.
- Перед боевым запуском остаётся: отдельная роль только для чтения под копии и отчёты, ротация паролей по
  расписанию, TLS до Postgres, если база уедет с хоста приложения.
