# ADR-0027. Нагрузочный тест: Locust и отдельный стек без обхода лимитов

- Статус: принято
- Дата: 2026-11-02

## Контекст
В #124 нужен нагрузочный тест базовых сценариев: вход по OTP, карта, аренда от брони до оплаты, телеметрия
парка и WebSocket у сотрудников. Он должен запускаться одной командой против локального Compose и против
стенда, в PowerShell и в Git Bash, а в CI — коротким дымовым прогоном.

Мешают защиты самого API. С одного IP можно запросить 20 кодов в час, клиенту можно загрузить 40 фото в час,
а поток парка закрывает сокет с неизвестным `Origin`. Отключать их ради теста нельзя (`CLAUDE.md`,
«Безопасность»), а настройки для этого в API нет.

## Решение
1. **Locust.** Отдельный Python-проект `tests/load` со своим `uv.lock`, запускается через `uv` и `npm run load:*`.
   Код API и эмулятора не меняется и зависимостей от теста не получает.
2. **Свой стек на запуск.** Локальный прогон поднимает Compose-проект `flagman-load` на своих портах со своей
   БД, своими случайными секретами и удаляет всё после прогона. Данные и контейнеры рабочего стека не
   затрагиваются, но образ `flagman-api:local` общий, и сборка его перезаписывает.
3. **Лимиты остаются включёнными.** Локально виртуальные пользователи получают разные адреса через
   `X-Forwarded-For` и `FORWARDED_ALLOW_IPS=*`. Это допустимо только в этом стеке: порты привязаны к 127.0.0.1 и
   живут один прогон. Лимиты на пользователя обходятся не настройкой, а размером пула клиентов. На стенде
   адреса не подменяются, поэтому профиль стенда маленький и укладывается в лимиты как есть.
4. **Клиенты готовятся через публичный API**, как в приложении: вход, документы, одобрение оператором, карта.
   Команды, которая пишет готового клиента прямо в БД, нет. Оператор одобряет только заявки с именем
   `Loadtest`: в очереди стенда могут быть настоящие.
5. **Телеметрию шлёт настоящий эмулятор.** Секрет телеметрии тесту не нужен, а задержка видна на потоке парка,
   то есть там же, где её видит сотрудник. Считается по часам сервера: у генератора нагрузки и сервера часы
   могут расходиться.

6. **Синхронный код.** Locust работает на потоках `gevent`, и его сценарии пишутся синхронно, поэтому подготовка
   клиентов тоже написана на `requests`. Это исключение из правила «async для I/O» только для `tests/load`: этот код
   не работает внутри API.

## Альтернативы
- **k6.** Быстрее на один процесс, но это отдельный бинарник: глобальная установка запрещена, а запуск через
  Docker на Windows требует возни с путями. TOTP и подготовку клиентов пришлось бы писать на `k6/crypto` и JS.
- **Настройка API, отключающая лимиты.** Проще всего, но такой выключатель однажды окажется включён на сервере.
  И замер перестал бы учитывать стоимость самих проверок лимитов.
- **Очистка Redis между шагами.** Работает только локально и только между шагами: лимит на IP сработает
  раньше, чем закончится подготовка пула.

## Последствия
- Замер показывает систему вместе с её лимитами, но генератор нагрузки и стек делят один компьютер, а локальные
  машины стоят на месте (`EMULATOR_SIMULATION_ENABLED=false`): движущаяся машина не могла бы завершить аренду.
- Прогон на стенде оставляет в его БД тестовых клиентов и поездки и требует выделенных номеров, поэтому запускается
  только по договорённости. Незавершённые аренды следующий прогон закрывает сам, а если не может, останавливается.
- Новые защиты API могут сломать подготовку пула или дымовой прогон. Это ожидаемо: тест правят вместе с защитой,
  а не наоборот.
