# Нагрузочный тест

Проверка, что пилот выдерживает базовые сценарии (#124). Инструмент и подход к лимитам описаны в
[ADR-0027](adr/0027-load-test-locust.md), код лежит в `tests/load`.

Здесь только нагрузочная часть задачи и **базовый замер, до оптимизаций**. Оптимизации и итоговый замер будут
после слияния #121: новые функции меняют горячие пути, и замер до них быстро устарел бы.

## Запуск

Нужны Docker, `uv` и `npm`. Команды одинаково работают в PowerShell и Git Bash.

| Команда | Что делает | Длительность |
|---|---|---|
| `npm run load:smoke` | Все сценарии на временном стеке, задержки не оцениваются. То же самое запускает CI | около 5 минут |
| `npm run load:local` | Профиль `pilot` на временном стеке, сверка с целями | около 13 минут |
| `npm run load:stand` | Маленький профиль на стенде, сначала нужно заполнить `tests/load/stand.env` | около 6 минут |

Код выхода: `0` — цели выполнены, `1` — прогон прошёл и есть промахи, `2` — прогон не удалось провести (нет Docker,
API недоступен, клиентов не удалось подготовить). Результаты складываются в
`tests/load/reports/<время>-<профиль>/`, git их не видит: `result.json` — сверка с целями, `summary.json` — итоговые
цифры, по которым она сделана, `locust_*.csv` — статистика (отстаёт от конца прогона на секунду), `stack.log` — логи
контейнеров.

Локальные команды поднимают Compose-проект `flagman-load` на своих портах (API — 18000) и удаляют его вместе с
данными. БД, порты и контейнеры рабочего стека они не трогают, но есть две оговорки. Сборка перезаписывает общий
образ `flagman-api:local`: он будет собран из текущей ветки. А запущенный рабочий стек добавит шум в замер.

Чтобы посмотреть на стек после прогона, добавьте `--keep`: `uv run --project tests/load flagman-load local smoke --keep`.
Настройки останутся в `stack.env` в папке отчёта, с ними стек и останавливается:
`docker compose --project-name flagman-load --env-file <папка отчёта>/stack.env --file infra/docker-compose.yml down --volumes`.
Следующий запуск удалит оставленный стек сам, вместе с данными.

Число процессов API задаёт `--api-workers N` (по умолчанию 1, как `API_WORKERS` у рабочего стека):
`uv run --project tests/load flagman-load local pilot --api-workers 2`. Так сравнивают один и несколько процессов
в одной серии прогонов.

**Стенд.** Время нужно согласовать с командой, чтобы не попасть на показ.

- **Номера.** Нужно 10 номеров из `SMS_FIXED_PHONES` только для теста, в примере настроек их два, так что список
  придётся расширить. Если у арендатора или клиента карты в профиле чужое имя, прогон остановится с кодом `2` до
  любых изменений профилей и заявок. На всех этих номерах к этому моменту уже будет выполнен вход, это новые сессии.
  Номера сценария входа заранее не проверяются: на них прогон только входит и ничего больше не делает.
- **Следы.** В БД стенда остаются тестовые клиенты с именем `Loadtest` и их поездки. Оператор одобряет только заявки
  клиентов этого прогона. Если чужие заявки заняли всю первую страницу очереди (100 штук), прогон остановится с кодом
  `2`.
- **Незавершённые аренды.** После конца прогона идущим арендам даётся 120 с на завершение. Если что-то осталось,
  следующий прогон сначала завершит эти аренды. Если машина уехала из зоны и завершить нельзя, или у клиента долг, он
  остановится с кодом `2`, и разобраться надо вручную.
- **Частота.** Один прогон в час: каждому клиенту можно загрузить 40 фото в час, и второму прогону их не хватит.
  Коды входа (10 из 20 в час на IP) ограничивают меньше.

## Сценарии

| Сценарий | Что делает | Профиль `pilot` |
|---|---|---|
| Карта | `GET /map/cars` и `/map/zones`, пауза 5–15 с | 200 клиентов |
| Вход | Запрос и проверка кода по OTP, пауза 5–10 с | 2 пользователя, 60 телефонов |
| Аренда | Бронь, 4 фото, открытие, поездка 1–2 минуты, 4 фото, завершение с оплатой через `FakeProvider` | 30 аренд, пул из 60 клиентов |
| Телеметрия | Настоящий эмулятор шлёт весь парк раз в 5 с | 50 машин |
| Поток парка | WebSocket у сотрудников, он же измеряет задержку телеметрии | 5 сотрудников |

- **Сбои.** Ошибкой считается любой неожиданный ответ, в том числе 429. Единственное исключение — 404
  `car-not-found` при брони: так API отвечает, когда машину только что занял другой клиент. Доля считается по
  каждому запросу отдельно, иначе отказ целого сценария потерялся бы среди запросов карты. Один случайный сбой в
  запросе не считается: в дымовом прогоне всего 7 входов.
- **Прогон не пройдёт** и при падении сценария внутри Locust, и при хотя бы одной неоплаченной аренде. Такая аренда не
  идёт в счёт завершённых, а её клиент выбывает из пула: с долгом нельзя бронировать.
- **50 машин вместо 30.** Аренду можно завершить только в зоне, а при `EMULATOR_SEED=42` в неё попадают 32 машины
  из 50 (из 30 — только 23). Телеметрии при этом больше, чем в настоящем парке, так что замер строже реальности.
- **Задержка телеметрии** считается только для сообщений со всем парком. Одна машина в сообщении — это ответ на
  команду, такие сообщения исказили бы процентиль самого тяжёлого пути.

## Цели

Записаны до первого прогона, в [плане задачи](https://github.com/luxsordel/flagman-drive/issues/124#issuecomment-6579909090).
В документах проекта чисел не было, это стартовые значения команды. Проверяются автоматически, в коде они лежат в
`tests/load/src/flagman_load/profiles.py`. Locust округляет процентили до двух значащих цифр, поэтому реальные 304 мс
в отчёте будут как 300 мс и пройдут цель 300 мс.

| Показатель | Цель |
|---|---|
| Одновременные аренды | 30, весь парк пилота |
| p95 карты | ≤ 300 мс |
| p95 входа по OTP | ≤ 500 мс |
| p95 брони, открытия, завершения | ≤ 1000 мс |
| p95 загрузки фото | ≤ 1500 мс |
| p95 задержки телеметрии до WebSocket | ≤ 2000 мс |
| Сбои | < 1% по каждому запросу |
| Неоплаченные аренды, падения сценариев | 0 |

## Базовый замер, 3 ноября 2026

Условия: `main` на коммите `19bb5b1`, уже с #112 и #122, и итоговый код теста. Один компьютер с Windows 11, Docker
Desktop (16 CPU, 16 ГБ), генератор нагрузки на том же компьютере. Профиль `pilot`, два прогона подряд. Каждый длится
10 минут, включая разгон около 47 с, и статистика за разгон не отбрасывается.

| Показатель | Цель | Прогон 1 | Прогон 2 | Итог |
|---|---|---|---|---|
| Пик одновременных аренд | ≥ 30 | 30 | 30 | выполнено |
| Завершённых аренд | ≥ 60 | 167 | 165 | выполнено |
| Сбои, худший запрос | < 1% | 0,09% | 0,11% | выполнено |
| Неоплаченные аренды, падения сценариев | 0 | 0 | 0 | выполнено |
| `GET /map/cars`, p95 | ≤ 300 мс | 500 мс | 670 мс | **промах** |
| `GET /map/zones`, p95 | ≤ 300 мс | 380 мс | 480 мс | **промах** |
| `POST /auth/otp/request`, p95 | ≤ 500 мс | 490 мс | 740 мс | **зависит от прогона** |
| `POST /auth/otp/verify`, p95 | ≤ 500 мс | 440 мс | 730 мс | **зависит от прогона** |
| `POST /rentals`, p95 | ≤ 1000 мс | 530 мс | 780 мс | выполнено |
| Открытие машины, p95 | ≤ 1000 мс | 1900 мс | 2800 мс | **промах** |
| Завершение аренды, p95 | ≤ 1000 мс | 2500 мс | 3400 мс | **промах** |
| Загрузка фото, p95 | ≤ 1500 мс | 1300 мс | 1700 мс | **зависит от прогона** |
| Задержка телеметрии, p95 | ≤ 2000 мс | 1200 мс | 1400 мс | выполнено |

**Вывод.** Пилот выдерживает нагрузку: весь парк в аренде, сбоев почти нет, все аренды оплачены. Но отвечает медленнее
целей. Открытие и завершение аренды не уложились в цель ни в одном из шести прогонов с этой нагрузкой, это главная
находка. Карта не уложилась в пяти из шести.

### Разброс между прогонами

На этом компьютере **одинаковый прогон может отличаться по p95 более чем вдвое**, поэтому одному прогону верить
нельзя. Все шесть прогонов с 50 машинами и 30 арендами:

| Показатель, p95 | 2 ноября, `e2560f9` | 3 ноября, `19bb5b1` | 3 ноября, итоговый код |
|---|---|---|---|
| `GET /map/cars` | 550 и 560 мс | 260 и 410 мс | 500 и 670 мс |
| Открытие машины | 2300 и 2500 мс | 1200 и 1600 мс | 1900 и 2800 мс |
| Завершение аренды | 2700 и 2500 мс | 1200 и 2500 мс | 2500 и 3400 мс |
| Загрузка фото | 1500 и 1500 мс | 820 и 1200 мс | 1300 и 1700 мс |

Четыре прогона 3 ноября шли подряд, между вторым и третьим были правки теста и дымовые прогоны, и почти все показатели
от прогона к прогону росли: карта 260, 410, 500, 670 мс. Итоговый код добавляет меньше 2% запросов, это
такой рост не объясняет. Похоже, что на скорость влияет состояние компьютера или Docker в длинной серии, но причину
мы не выясняли.

Чтобы сравнивать «до и после», нужно чередовать варианты в одной серии (A, B, A, B), а не снимать их друг за другом:
иначе рост внутри серии можно принять за эффект правки. Различие меньше двух раз без этого не доказано.

### Что видно в замере

- **API упирался в один процесс, база — нет.** Снимки `docker stats` раз в 30 с сделаны в одном прогоне 2 ноября, в
  остальных их не снимали. Процесс API занимал в среднем 91% ядра, пики до 167% (100% — одно ядро). В образе запущен
  один процесс uvicorn. Остальные не загружены: Postgres 8,5%, SeaweedFS 7%, Redis 1%, эмулятор 0,3%.
- **Хвост длинный.** Медиана карты 100–110 мс, а p95 — 500–670 мс. Похоже на ожидание в очереди процесса, но это
  гипотеза.
- **Единичные сбои.** В каждом прогоне 10–13 запросов карты и зон оборвались без ответа (`ConnectionError`), других
  сбоев нет. В одном прогоне 2 ноября открытие машины получило 504 `telematics-timeout`, аренда корректно отменилась.
  Причину этого 504 не разбирали.

### Что проверить при оптимизации

Это гипотезы по чтению кода, замером они не подтверждены. Каждую оптимизацию подтверждаем замером до и после.

1. **Перекодирование фото.** `clean_photo` (`core/photos.py`) декодирует и заново кодирует каждое фото с
   `optimize=True`. Это идёт в потоке, но в том же процессе, а фото приходят примерно 2,4 в секунду. Похоже на
   главного потребителя CPU.
   Не подтвердилось: перекодирование занимает около 0,45 ядра в потоках, а узкое место — цикл событий. Цикл на
   загрузке фото тратил время на новый клиент S3, это исправлено, см.
   [«Один клиент хранилища на процесс»](#один-клиент-хранилища-на-процесс). Замер `optimize` — в
   [«Перекодирование фото»](#перекодирование-фото).
2. **Запись телеметрии.** На каждую машину свой `UPDATE` в одной транзакции (`fleet/service.py`), всё это раз в 5 с
   и даже для стоящих машин. Транзакция держит блокировки строк машин, а бронь и команды пишут в те же строки.
   Возможная причина долгих p95 у открытия и завершения.
   Подтвердилось: 55 операторов на пакет и ожидания блокировок строк машин под нагрузкой. Исправлено, правка
   подтверждена микробенчем, прогоном `pilot` пока не мерилась, см. [«Пакетная запись телеметрии»](#пакетная-запись-телеметрии).
3. **Один процесс uvicorn.** Несколько процессов могут дать запас сразу, но поток парка рассылает сообщения изнутри
   процесса: сначала надо проверить, что это не сломает его ([ADR-0017](adr/0017-fleet-stream-websocket.md)).
   Подтвердилось и исправлено, поток парка работает, см. [«Несколько процессов API»](#несколько-процессов-api).
4. **Пул соединений с БД.** Сейчас значения SQLAlchemy по умолчанию, настройки нет (`core/db.py`).
   Подтвердилось: в прогоне `pilot` API и worker открывали около 1,8 новых соединения в секунду. Исправлено,
   правка подтверждена микробенчем, прогоном `pilot` пока не мерилась, см. [«Настраиваемый пул БД»](#настраиваемый-пул-бд).
5. **Обрывы запросов карты.** Возможно, это гонка keep-alive: у uvicorn по умолчанию 5 с, а пауза клиента 5–15 с.
   Подтвердилось и исправлено, правка подтверждена отдельным замером, прогоном `pilot` пока не мерилась, см.
   [«Keep-alive API»](#keep-alive-api).

## Оптимизации (#162)

Каждая правка подтверждена замером до и после, варианты чередовались в одной серии (см. «Разброс между прогонами»).
Условия те же, что у базового замера: тот же компьютер, рабочий стек остановлен, во время прогонов ничего тяжёлого
не запускалось.

### Несколько процессов API

**Что нашли.** API упирается в один цикл событий, а не в базу. В прогоне `pilot` профилировщик `py-spy` показал,
что главный поток процесса API занят 83,5% времени, а в Postgres в среднем 0,34 активных соединения. Процесс API
при этом занимал около одного ядра, остальные контейнеры почти простаивали.

**Что сделали.** Число процессов uvicorn задаёт `API_WORKERS` (по умолчанию 1, поведение не меняется, пока
настройку не задали), в нагрузочном тесте — `--api-workers N`. Поток парка от этого не ломается: каждый процесс сам
слушает `fleet_changes` в Postgres и рассылает изменения своим сокетам, периодические задачи живут в
`flagman-worker`, лимиты запросов — в Redis ([ADR-0017](adr/0017-fleet-stream-websocket.md)). Цена — память и
соединения с БД: каждый процесс держит свой пул и одно соединение слушателя, контейнер API занимал 128 МиБ с одним
процессом и 279 МиБ с двумя. Бюджет соединений описан в `.env.example`.

**Замер до и после.** 6–7 ноября 2026, ветка `chore/162-optimization-security-review` с этой правкой. Четыре
прогона `npm run load:local` подряд, процессы чередовались 1, 2, 1, 2
(`uv run --project tests/load flagman-load local pilot --api-workers N`):

| Показатель, p95 | Цель | 1 процесс | 2 процесса | 1 процесс | 2 процесса |
|---|---|---|---|---|---|
| `GET /map/cars` | ≤ 300 мс | 240 мс | 58 мс | 270 мс | 66 мс |
| `GET /map/zones` | ≤ 300 мс | 150 мс | 40 мс | 190 мс | 37 мс |
| `POST /auth/otp/request` | ≤ 500 мс | 250 мс | 58 мс | 370 мс | 56 мс |
| `POST /auth/otp/verify` | ≤ 500 мс | 240 мс | 72 мс | 290 мс | 42 мс |
| `POST /rentals` | ≤ 1000 мс | 270 мс | 89 мс | 290 мс | 110 мс |
| Открытие машины | ≤ 1000 мс | **1100 мс** | 230 мс | **1000 мс** | 310 мс |
| Завершение аренды | ≤ 1000 мс | **1300 мс** | 290 мс | **1200 мс** | 380 мс |
| Загрузка фото | ≤ 1500 мс | 730 мс | 320 мс | 870 мс | 350 мс |
| Задержка телеметрии | ≤ 2000 мс | 610 мс | 290 мс | 640 мс | 280 мс |
| Сообщений с телеметрией в потоке парка | ≥ 100 | 564 | 557 | 559 | 569 |
| Завершённых аренд | ≥ 60 | 171 | 176 | 173 | 172 |
| Итог | | промах | выполнено | промах | выполнено |

С двумя процессами p95 ниже в 2–5 раз по всем запросам, и прогон впервые укладывается во все цели. Разница больше
разброса между прогонами: худший прогон с двумя процессами быстрее лучшего с одним по каждому показателю. Сбоев по
1–2 `ConnectionError` у карты на прогон, неоплаченных аренд и падений сценариев нет ни в одном из четырёх.

Один процесс в этой серии отвечал заметно быстрее, чем в базовом замере 3 ноября (карта 240–270 мс против
500–670 мс). Между ними и правки ветки, и другое состояние компьютера, поэтому сравнивать можно только прогоны
внутри серии.

**Поток парка с двумя процессами.** Пять сотрудников получают столько же сообщений с телеметрией, сколько с одним
процессом (557 и 569 против 564 и 559). Если бы процесс рассылал только свои изменения, сокеты на другом процессе
недосчитались бы примерно половины. Во втором прогоне с двумя процессами соединения внутри контейнера API разобраны
по процессам: из пяти долгоживущих соединений (сокеты сотрудников) одно держал один процесс, четыре — другой, а все
три снятых в это время запроса телеметрии от эмулятора обрабатывал второй. Значит, сотрудник на первом процессе
получал телеметрию, записанную вторым.

**Отдельный замер карты.** Чтобы отделить эффект от остальной нагрузки, карту мерили и отдельно, на том же стеке
`flagman-load` с 300 машинами: замкнутый цикл 20 с, `GET /map/cars` и `/map/zones` в пропорции 5:1, процессы
чередовались 1, 2, 1, 2. Скрипт был разовым и в репозиторий не вошёл, основное подтверждение — прогоны выше.

| Запросов одновременно | 1 процесс | 2 процесса |
|---|---|---|
| 32 | 97 и 95 запросов/с, p95 488 и 505 мс | 179 и 182 запроса/с, p95 298 и 296 мс |
| 8 | 99 и 99 запросов/с, p95 147 и 143 мс | 194 и 196 запросов/с, p95 67 и 65 мс |

Процессорное время на запрос не изменилось (11,7–12,9 мс), второй процесс просто занимает второе ядро.

### Один клиент хранилища на процесс

**Что нашли.** `S3ObjectStorage` (`core/storage.py`) создавал новый клиент `aiobotocore` на каждый `put`, `delete`
и `signed_get_url`: разбор модели сервиса S3, копия хуков `botocore`, коннектор `aiohttp` и SSL-контекст. Всё это
выполняется в цикле событий. В прогоне `pilot` `py-spy` насчитал на `botocore` внутри загрузки фото осмотра 12,3%
сэмплов главного потока (923 из 7497), из них 357 на создание клиента и 292 на создание коннектора. Фото под
нагрузкой приходят примерно 2,4 в секунду.

**Что сделали.** Хранилище открывается один раз на процесс в `lifespan` приложения (`open_object_storage`) и лежит
в `Resources.storage`. В нём два клиента: внутренний для записи и удаления и клиент публичного адреса, который
только подписывает ссылки. При остановке оба закрываются. Клиент `aiobotocore` можно использовать из многих запросов
одного цикла, соединения с хранилищем держит пул `aiohttp`. Без ключей `S3_ACCESS_KEY` / `S3_SECRET_KEY` хранилища
по-прежнему нет, и загрузки отвечают 503. Открытие никуда не подключается, поэтому API стартует и при недоступном
хранилище. Новых настроек нет.

Это меняет поведение при зависшем хранилище. Раньше у каждого `put` и `delete` был свой коннектор, и число соединений
ничем не ограничивалось. Теперь у процесса общий пул на 10 соединений (`_MAX_CONNECTIONS`, столько же по умолчанию в
`botocore`). `aiobotocore` задаёт `aiohttp` только тайм-ауты сокета, поэтому без ограничения вызов ждал бы
свободное соединение сколько угодно: десять зависших загрузок (до 30 с чтения × 3 попытки) остановили бы все
остальные загрузки и удаления процесса. Поэтому `put` и `delete` ждут свободное соединение не дольше тайм-аута
подключения, 5 с, и потом падают с `TimeoutError` (ответ 500, как и при недоступном хранилище раньше). Подпись
ссылок соединений не занимает и от этого не зависит. При пилотной нагрузке процессу в среднем нужно меньше одного
соединения (2,4 фото в секунду по ~25 мс), так что предел на замеры не влияет.

### Перекодирование фото

**Что проверяли.** Гипотеза 1: `clean_photo` (`core/photos.py`) перекодирует каждое фото с `optimize=True`, и это
главный потребитель CPU. Правку не делали, ниже замер, почему.

**Замер.** Профиль `py-spy` того же прогона `pilot` (один процесс, до правки хранилища, 7497 тактов): потоки
перекодирования были заняты в 3355 сэмплах, то есть в среднем около 0,45 ядра, из них на кодирование (`save`) 1142,
около 0,15 ядра. Главный поток с циклом событий был занят почти всё время, около одного ядра. Перекодирование идёт
в других потоках и на других ядрах, а Pillow отпускает GIL, поэтому цикл оно не держит. Узкое место — цикл,
см. [«Несколько процессов API»](#несколько-процессов-api).

Микробенч 7 ноября 2026, Pillow 13.0.0, тот же код, что в `clean_photo`, с `optimize=True` и `False`. Блоки по 20
вызовов, варианты чередовались три раза; на одно фото:

| Фото | `optimize=True`: CPU | Размер | `optimize=False`: CPU | Размер |
|---|---|---|---|---|
| Фото нагрузочного теста, 797 КБ | 66–67 мс | 841 КБ | 43–45 мс | 973 КБ (+16%) |
| Более гладкое фото, 562 КБ | 56–57 мс | 617 КБ | 38–39 мс | 649 КБ (+5%) |

**Вывод.** `optimize=False` экономит около трети CPU перекодирования, при пилотной нагрузке это примерно 0,05 ядра,

занимает, а у компьютера замера 16 ядер, и большая часть простаивала. `optimize=False` решили включать
только при явном измеренном выигрыше, его нет, поэтому `optimize=True` оставили. Пересмотреть стоит на сервере с 2–4 ядрами,
если процессы API и перекодирование начнут делить ядра: тогда сравнить p95 загрузки фото с обоими вариантами.

### Одна транзакция для карты

**Что нашли.** `GET /map/cars` — самый частый запрос: около 16 в секунду, 9524 за прогон `pilot`, примерно половина
всех операторов SQL при пилотной нагрузке. На оставленном стеке `pg_stat_statements` насчитал на один запрос карты
10 операторов: `BEGIN` ×4, `COMMIT` ×2, `ROLLBACK` ×2 и по одному `SELECT` машин и тарифов. Ещё два `;` в
статистику не попадают: это `pool_pre_ping`, который в SQLAlchemy 2.1 с asyncpg на каждое взятие соединения из пула
делает `BEGIN`, `;`, `ROLLBACK`. Причина — `pricing.current_versions` и `fleet.find_cars_on_map` открывали каждый
свою транзакцию, и между ними соединение возвращалось в пул и бралось снова. Итого 12 обменов с базой ради двух
полезных запросов. Сами запросы дешёвые: по `pg_stat_statements` машины выполняются в среднем за 1,49 мс, тарифы
за 0,06 мс, `EXPLAIN (ANALYZE, BUFFERS)` ничего плохого не показал. Дорого именно число обменов: каждый — это
ожидание ответа и очередной проход цикла событий, который и так узкое место.

**Что сделали.** `list_map_cars` и `get_map_car` (`fleet/api.py`) читают тарифы и машины в одной транзакции
`async with db.begin()`. Помощники `_read` в `pricing` и `fleet` уже присоединяются к открытой транзакции, поэтому
сервисы не менялись. Транзакция в роутере — граница запроса, а не бизнес-логика. Оба `SELECT` по-прежнему
выполняются в `READ COMMITTED`, каждый со своим снимком, так что ответ тот же. Теперь на запрос 7 обменов:
`BEGIN`, `;`, `ROLLBACK` от pre-ping, `BEGIN`, два `SELECT`, `COMMIT`; в `pg_stat_statements` 6 операторов вместо 10.
Тест `test_the_map_reads_tariffs_and_cars_in_one_transaction` проверяет одно взятие из пула, одну транзакцию и два
запроса на список и на карточку машины.

### Настраиваемый пул БД

**Что нашли.** `create_engine` (`core/db.py`) создавал движок со значениями SQLAlchemy по умолчанию:
5 постоянных соединений и до 10 сверх них. Соединение сверх пула закрывается, как только его вернули, и при
следующем всплеске открывается заново. В прогоне `pilot` счётчик `pg_stat_database.sessions` за 540 с нагрузки вырос
с 186 до 1276: 1090 новых сессий. Не все они от API: healthcheck `postgres` в Compose раз в 5 с вызывает
`pg_isready -d flagman`, а он входит через локальный сокет с `trust` и открывает настоящую сессию в базе `flagman`.
Каждый вызов `pg_isready`, как и каждый замер через `psql`, добавляет к счётчику ровно одну сессию (проверено
на отдельном контейнере `postgis/postgis:16-3.6`: 20 вызовов — 20 сессий). За 540 с это около 108 сессий
healthcheck, так что на API и worker приходится не больше 982, около 1,8 в секунду. По `pg_stat_activity`
соединений в среднем 10,3, максимум 18.
Номера подготовленных выражений asyncpg дошли до `__asyncpg_stmt_28c1__`, около 10 тысяч подготовок: кэш выражений
живёт в соединении и пропадает вместе с ним. Отдельный замер одного подключения (100 повторов, `select 1`): новое
соединение — 20,6 мс и 8,4 мс CPU, взятое из пула с `pool_pre_ping` — 5,6 мс и 1,25 мс CPU.

**Что сделали.** Размер пула задают `DB_POOL_SIZE` (по умолчанию 10, от 1 до 50) и `DB_MAX_OVERFLOW` (по умолчанию
10, от 0 до 50), они общие для процессов API и `flagman-worker` и передаются через Compose. Остальное поведение
движка не менялось. Бюджет соединений: `(API_WORKERS + 1) × (DB_POOL_SIZE + DB_MAX_OVERFLOW) + API_WORKERS` меньше
`max_connections` Postgres (100); с двумя процессами по умолчанию это 62. Предел на процесс вырос с 15 до 20, поэтому
по умолчанию в бюджет помещается не больше трёх процессов API (было пять); для большего числа нужно уменьшить пул
или поднять `max_connections`. Формула — в `.env.example`, короче — в
`infra/stand/stand.env.example` и [docs/02](02-architecture.md). Тесты в `tests/test_config.py` проверяют, что пул
движка берёт размеры из настроек, значения по умолчанию у API и worker и отказ от значений вне диапазона.

**Замер до и после.** 7 ноября 2026, микробенч на `testcontainers` (`postgis/postgis:16-3.6` в Docker Desktop),
движок с теми же параметрами, что в `create_engine`, кроме размеров пула. Запросы приходят пуассоновским потоком
120 в секунду, каждый держит соединение на 6 обменов `select 1` с паузами 2–10 мс между ними (как запрос, который

а пики одновременных запросов в замере выше обоих пределов, и часть запросов ждёт очереди пула. Чтобы отделить
выигрыш от постоянных соединений от выигрыша от более высокого предела, в серию добавлен вариант 5 + 15 с тем же
пределом 20, что и у новой настройки. Варианты чередовались 5/10, 5/15, 10/10, 5/10, 5/15, 10/10. Новые соединения
считались событием `connect` пула и сверялись с приростом `pg_stat_database.sessions`, оба счётчика совпали.

| Показатель | 5 + 10 (до) | 5 + 15 (тот же предел 20) | 10 + 10 (после) |
|---|---|---|---|
| Новых соединений в секунду | 25,3 и 23,4 | 27,8 и 29,6 | 3,5 и 3,7 |
| CPU процесса на запрос | 4,58 и 4,50 мс | 4,79 и 4,86 мс | 3,34 и 3,37 мс |

| Запросов одновременно, среднее / пик | 5,7 / 30 и 5,5 / 31 | 6,5 / 35 и 6,6 / 34 | 3,6 / 24 и 3,7 / 30 |

С тем же пределом 20, но пятью постоянными соединениями (5 + 15) очередь пула короче, чем у старой настройки, а
переподключений и CPU больше, и запросы не быстрее, а медленнее: каждое лишнее соединение сверх пула открывается
заново. Значит, выигрыш 10 + 10 дают постоянные соединения, а не более высокий предел. Новая настройка ещё и почти
убирает ожидание очереди (до 0,8% запросов), но только потому, что запросы с постоянными соединениями короче и их
одновременно меньше.

Микробенч нарочно жёстче прогона `pilot`: все его запросы держат соединение, поэтому всплески выше и
переподключений больше, чем 1,8 в секунду под настоящей нагрузкой. Его цифры — не ожидание для `pilot`, а
направление и цена: каждое сэкономленное подключение — около 7 мс CPU цикла событий и несколько обменов с базой.
Прогоном `pilot` эта правка пока не мерилась. Ожидание для него: переподключения API почти исчезнут (пик был
18 соединений на всю базу, то есть всплески API редко выходят за 10), экономия около 13 мс CPU в секунду.
Проверить это можно по приросту `pg_stat_database.sessions` за прогон, как в разделе «Что нашли», но из прироста
надо вычесть сессии, которые API не открывал: по одной на каждый healthcheck (длительность прогона / 5 с, около
0,2 в секунду) и на каждый замер через `psql`. Даже без единого переподключения API счётчик будет расти примерно
на 0,2 в секунду.

### Keep-alive API

**Что нашли.** uvicorn закрывает простаивающее keep-alive соединение через 5 с: это его собственное значение
`--timeout-keep-alive`, настройки у нас не было. Клиенты прогона делают между запросами карты паузы 5–15 с. Если
запрос уходит в соединение в тот момент, когда uvicorn его закрывает, ответа нет: `ConnectionError` с
`RemoteDisconnected`. Это и есть единичные сбои карты и зон в каждом прогоне (в прогоне диагностики 8 на
11,4 тыс. запросов карты). Гонку воспроизвёл отдельный скрипт: 50 потоков, у каждого своя keep-alive сессия и
10 запросов `/health`. При паузе 3,0–3,5 с обрывов 0 из 500, при паузе 4,95–5,05 с — 2 из 500.
На стенде такая же гонка возможна между Caddy и API. Caddy держит простаивающее соединение к upstream 2 минуты
(значение по умолчанию), дольше uvicorn. Go сам повторяет такой запрос только для идемпотентных методов, поэтому
POST вместо ответа получил бы 502.

**Что сделали.** Compose передаёт uvicorn `UVICORN_TIMEOUT_KEEP_ALIVE` из новой настройки `API_KEEP_ALIVE_SECONDS`,
по умолчанию 75 с. Это больше пауз клиентов и больше простоя Caddy. В Caddyfile стенда оба прокси к API вынесены в
сниппет `(api)` с `transport http { keepalive 60s }`. Теперь Caddy бросает простаивающее соединение раньше, чем его
закроет uvicorn, а закрытие на стороне Caddy гонки не даёт: новый запрос просто откроет новое соединение. Настройка
описана в `.env.example` и `infra/stand/stand.env.example`, стек `flagman-load` берёт значение по умолчанию из
Compose. Код API не менялся. Цена — простаивающие сокеты: клиент держит соединение до 75 с вместо 5 с. При нагрузке
пилота это сотни сокетов, не тысячи.

**Замер до и после.** 7 ноября 2026, стек `flagman-load` с одним `api` и его зависимостями, образ собран из ветки.

| GET, пауза 4,95–5,05 с, 50 × 20: обрывов | 19 из 1000 | 0 из 1000 | 17 из 1000 | 0 из 1000 |

стенда (`caddy:2.10.2-alpine`) с 25 сайтами, у каждого свой пул соединений к API и свой поток клиента, чтобы
соединение к API простаивало ровно столько, сколько пауза клиента. Варианты: Caddy по умолчанию и uvicorn 5 с, затем
`keepalive 60s` и uvicorn 75 с, дважды через один. На 500 GET и 500 POST с паузой 4,95–5,05 с в каждом варианте
обрывов и 502 нет ни в одном. Внутри сети Docker закрытие соединения доходит до Caddy за доли миллисекунды, и окно
гонки намного уже, чем через проброшенный порт Docker Desktop. Поэтому правка Caddyfile — согласование тайм-аутов
по документации Caddy и uvicorn, а не исправление измеренного сбоя. То, что Caddy применяет 60 с к обоим прокси к API,
проверено через `caddy adapt` (`keep_alive.idle_timeout` 60 с) и `node scripts/check-caddy.mjs`.

Прогоном `pilot` правка пока не мерилась. Ожидание для него: `ConnectionError` у карты и зон 0 за прогон вместо
1–13.

### Пакетная запись телеметрии

**Что нашли.** Эмулятор раз в 5 с шлёт весь парк одним вебхуком, а `receive_telemetry` (`fleet/service.py`)
применял снимки по одному: свой `UPDATE cars` на машину внутри одной транзакции. По `pg_stat_statements` на
оставленном стеке (30 с, 6 пакетов по 50 машин) на пакет приходилось 55,17 оператора: 50 `UPDATE`, `BEGIN` ×2,
`COMMIT`, `ROLLBACK` от pre-ping и `pg_notify`. В самой базе это всего 5,48 мс на пакет, но 50 обменов идут подряд,
и всё это время транзакция держит блокировки строк уже обновлённых машин. На простаивающем стеке пакет из 100
`UPDATE` шёл от первого оператора до `COMMIT` 103–107 мс (`log_min_duration_statement=0`). Под нагрузкой (порог
200 мс) половина медленных операторов — `UPDATE` телеметрии на 200–540 мс, то есть ожидание блокировок, и дважды
`SELECT ... FOR UPDATE` по `cars` ждал больше секунды (`log_lock_waits`: 1051 и 1304 мс). Состояние уходит в поток
парка только после `COMMIT`, поэтому длина транзакции прямо входит в задержку телеметрии.

**Что сделали.** `repository.apply_states` (`fleet/repository.py`) записывает весь пакет одним
`UPDATE cars ... FROM unnest(...) AS s(...) WHERE cars.telematics_id = s.telematics_id AND (cars.state_at IS NULL
OR cars.state_at < s.recorded_at) RETURNING ...`. Проверка свежести та же, что у одиночного `apply_state`, по каждой
машине. Снимки передаются десятью типизированными массивами, а не строками `VALUES`: текст оператора и число
параметров не зависят от размера пакета, и подготовленный оператор asyncpg переиспользуется. Точка собирается
в SQL из чисел через `ST_MakePoint`, как в `_geography`, SQL из строк нет. Неприменённые снимки делит на
устаревшие и неизвестные машины один `SELECT ... WHERE telematics_id = ANY(...)`, и только если такие есть.
`receive_telemetry` проверяет время снимков в Python, как раньше, из нескольких снимков одной машины в пакете
оставляет самый свежий (остальные `stale`, см. [docs/02](02-architecture.md)), и по-прежнему шлёт одно уведомление
на пакет. Путь одного снимка (`apply_state_snapshot`, ответ на команду машине) не менялся. Тесты в
`fleet/tests/test_service.py`: смесь применённых, устаревших, неизвестных и «из будущего» в одном пакете, несколько
снимков одной машины, пакет старше сохранённого состояния, пустой пакет.

**Замер до и после.** 7 ноября 2026, микробенч на `testcontainers` (`postgis/postgis:16-3.6` с
`pg_stat_statements` в Docker Desktop), старый путь (цикл `apply_state`) и новый `receive_telemetry` в одном
процессе. На прогрев по 5 пакетов, затем 10 пакетов на счёт операторов и 200 пар пакетов, старый и новый через один.
Все снимки свежие, то есть каждый пакет обновляет каждую машину. Время — от входа в функцию до выхода, то есть
вся транзакция с `COMMIT`; CPU — процессорное время процесса Python на пакет (то же время цикла событий в API).

| Показатель | 50 машин, до | 50 машин, после | 100 машин, до | 100 машин, после |
|---|---|---|---|---|
| Операторов на пакет (`pg_stat_statements`) | 55,4 | 6,4 | 105,4 | 6,4 |
| Время пакета, медиана | 119,8 мс | 11,8 мс | 233,4 мс | 14,6 мс |
| Время пакета, p95 | 134,5 мс | 13,5 мс | 261,3 мс | 17,0 мс |
| CPU процесса на пакет, среднее | 77,2 мс | 5,1 мс | 148,4 мс | 6,6 мс |

Дробная часть операторов — фоновые `BEGIN`, `COMMIT` и `ROLLBACK` соединения самого замера. После правки на
пакет: `BEGIN`, `;` и `ROLLBACK` от pre-ping, `BEGIN`, один `UPDATE`, `pg_notify`, `COMMIT`; `SELECT` по
неприменённым в замере не нужен. `EXPLAIN (ANALYZE, BUFFERS)` нового `UPDATE` на 100 машинах: `Hash Join`
таблицы `cars` (`Seq Scan`, 150 строк) с `Function Scan` по `unnest`, выполнение 2,2 мс, из них 0,5 мс — проверка
внешнего ключа на модель, она была и у старых `UPDATE`. При малом парке строки блокируются в порядке таблицы,
у большого планировщик может выбрать вложенный цикл по индексу `telematics_id`, тогда — в порядке
отсортированного пакета.

Транзакция пакета короче в 10–16 раз и держит блокировки строк столько же меньше. Время здесь больше, чем 103–107 мс
на стеке, потому что обмен с базой идёт через проброшенный порт Docker Desktop, а не по сети Docker: выигрыш на стеке
по абсолютной величине будет меньше, но обменов на пакет всё равно 6 вместо 55. CPU цикла событий на пакет 50 машин
снизился примерно на 70 мс, то есть около 1,4% одного ядра при пакете раз в 5 с. Прогоном `pilot` правка пока
не мерилась. Ожидание для него: меньше ожиданий блокировок у брони, открытия и завершения и ниже p95 задержки
телеметрии.

## Ограничения замера

- Генератор нагрузки делит компьютер со стеком, а между ними нет настоящей сети. На сервере абсолютные значения будут
  другими, а между прогонами они различаются более чем вдвое (см. «Разброс между прогонами»).
- Локально машины стоят на месте (`EMULATOR_SIMULATION_ENABLED=false`), иначе арендованная машина уезжает и не может
  завершить аренду. Телеметрия при этом идёт по расписанию, а тяжёлая часть сценария работает как обычно.
- **На стенде прогон ещё не запускался.** Это критерий #124 «запуск одной командой против стенда», он остаётся
  открытым. Юнит-тестами покрыты только план стенда, отмена брони при уехавшей машине и вход без подмены адреса.
  Настоящие движущиеся машины, один токен на два сокета и лимиты стенда ничем не проверены.
- В логах прогонов простой поиск не нашёл токенов и телефонов. Это не заменяет проверку логов из чек-листа
  безопасности, которая остаётся в #124.
