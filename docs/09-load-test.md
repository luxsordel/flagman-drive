# Нагрузочный тест

Проверка, что пилот выдерживает базовые сценарии (#124). Инструмент и подход к лимитам описаны в
[ADR-0027](adr/0027-load-test-locust.md), код лежит в `tests/load`.

Здесь только нагрузочная часть задачи и **базовый замер, до оптимизаций**. Оптимизации и итоговый замер будут
после слияния #121: новые функции меняют горячие пути, и замер до них быстро устарел бы.

## Запуск

Нужны Docker, `uv` и `npm`. Команды одинаково работают в PowerShell и Git Bash.

| Команда | Что делает | Длительность |
|---|---|---|
| `npm run load:smoke` | Все сценарии на временном стеке, задержки не оцениваются. То же самое запускает CI | около 5 минут |
| `npm run load:local` | Профиль `pilot` на временном стеке, сверка с целями | около 13 минут |
| `npm run load:stand` | Маленький профиль на стенде, сначала нужно заполнить `tests/load/stand.env` | около 6 минут |

Код выхода: `0` — цели выполнены, `1` — прогон прошёл и есть промахи, `2` — прогон не удалось провести (нет Docker,
API недоступен, клиентов не удалось подготовить). Результаты складываются в
`tests/load/reports/<время>-<профиль>/`, git их не видит: `result.json` — сверка с целями, `locust_*.csv` —
статистика, `stack.log` — логи контейнеров.

Локальные команды поднимают Compose-проект `flagman-load` на своих портах (API — 18000) и удаляют его вместе с
данными. БД, порты и контейнеры рабочего стека они не трогают, но есть две оговорки. Сборка перезаписывает общий
образ `flagman-api:local`: он будет собран из текущей ветки. А запущенный рабочий стек добавит шум в замер.

Чтобы посмотреть на стек после прогона, добавьте `--keep`: `uv run --project tests/load flagman-load local smoke --keep`.
Настройки останутся в `stack.env` в папке отчёта, с ними стек и останавливается:
`docker compose --project-name flagman-load --env-file <папка отчёта>/stack.env --file infra/docker-compose.yml down --volumes`.
Следующий запуск удалит оставленный стек сам, вместе с данными.

**Стенд.** Время нужно согласовать с командой, чтобы не попасть на показ.

- **Номера.** Нужно 10 номеров из `SMS_FIXED_PHONES` только для теста, в примере настроек их два, так что список
  придётся расширить. Если у арендатора или клиента карты в профиле чужое имя, прогон остановится с кодом `2` до
  любых изменений профилей и заявок. На всех этих номерах к этому моменту уже будет выполнен вход, это новые сессии.
  Номера сценария входа заранее не проверяются: на них прогон только входит и ничего больше не делает.
- **Следы.** В БД стенда остаются тестовые клиенты с именем `Loadtest` и их поездки. Оператор одобряет только их
  заявки. Если настоящие заявки заняли всю первую страницу очереди (100 штук), прогон остановится с кодом `2`.
- **Незавершённые аренды.** После конца прогона идущим арендам даётся 120 с на завершение. Если что-то осталось,
  следующий прогон сначала завершит эти аренды. Если машина уехала из зоны и завершить нельзя, или у клиента долг, он
  остановится с кодом `2`, и разобраться надо вручную.
- **Частота.** Один прогон в час: каждому клиенту можно загрузить 40 фото в час, и второму прогону их не хватит.
  Коды входа (10 из 20 в час на IP) ограничивают меньше.

## Сценарии

| Сценарий | Что делает | Профиль `pilot` |
|---|---|---|
| Карта | `GET /map/cars` и `/map/zones`, пауза 5–15 с | 200 клиентов |
| Вход | Запрос и проверка кода по OTP, пауза 5–10 с | 2 пользователя, 60 телефонов |
| Аренда | Бронь, 4 фото, открытие, поездка 1–2 минуты, 4 фото, завершение с оплатой через `FakeProvider` | 30 аренд, пул из 60 клиентов |
| Телеметрия | Настоящий эмулятор шлёт весь парк раз в 5 с | 50 машин |
| Поток парка | WebSocket у сотрудников, он же измеряет задержку телеметрии | 5 сотрудников |

- **Сбои.** Ошибкой считается любой неожиданный ответ, в том числе 429. Единственное исключение — 404
  `car-not-found` при брони: так API отвечает, когда машину только что занял другой клиент. Доля считается по
  каждому запросу отдельно, иначе отказ целого сценария потерялся бы среди запросов карты. Один случайный сбой в
  запросе не считается: в дымовом прогоне всего 7 входов.
- **Прогон не пройдёт** и при падении сценария внутри Locust, и при хотя бы одной неоплаченной аренде. Такая аренда не
  идёт в счёт завершённых, а её клиент выбывает из пула: с долгом нельзя бронировать.
- **50 машин вместо 30.** Аренду можно завершить только в зоне, а при `EMULATOR_SEED=42` в неё попадают 32 машины
  из 50 (из 30 — только 23). Телеметрии при этом больше, чем в настоящем парке, так что замер строже реальности.
- **Задержка телеметрии** считается только для сообщений со всем парком. Одна машина в сообщении — это ответ на
  команду, такие сообщения исказили бы процентиль самого тяжёлого пути.

## Цели

Записаны до первого прогона, в [плане задачи](https://github.com/luxsordel/flagman-drive/issues/124#issuecomment-6579909090).
В документах проекта чисел не было, это стартовые значения команды. Проверяются автоматически, в коде они лежат в
`tests/load/src/flagman_load/profiles.py`. Locust округляет процентили до двух значащих цифр, поэтому реальные 304 мс
в отчёте будут как 300 мс и пройдут цель 300 мс.

| Показатель | Цель |
|---|---|
| Одновременные аренды | 30, весь парк пилота |
| p95 карты | ≤ 300 мс |
| p95 входа по OTP | ≤ 500 мс |
| p95 брони, открытия, завершения | ≤ 1000 мс |
| p95 загрузки фото | ≤ 1500 мс |
| p95 задержки телеметрии до WebSocket | ≤ 2000 мс |
| Сбои | < 1% по каждому запросу |
| Неоплаченные аренды, падения сценариев | 0 |

## Базовый замер, 3 ноября 2026

Условия: `main` на коммите `19bb5b1`, уже с #112 и #122, и итоговый код теста. Один компьютер с Windows 11, Docker
Desktop (16 CPU, 16 ГБ), генератор нагрузки на том же компьютере. Профиль `pilot`, два прогона подряд. Каждый длится
10 минут, включая разгон около 47 с, и статистика за разгон не отбрасывается.

| Показатель | Цель | Прогон 1 | Прогон 2 | Итог |
|---|---|---|---|---|
| Пик одновременных аренд | ≥ 30 | 30 | 30 | выполнено |
| Завершённых аренд | ≥ 60 | 167 | 165 | выполнено |
| Сбои, худший запрос | < 1% | 0,09% | 0,11% | выполнено |
| Неоплаченные аренды, падения сценариев | 0 | 0 | 0 | выполнено |
| `GET /map/cars`, p95 | ≤ 300 мс | 500 мс | 670 мс | **промах** |
| `GET /map/zones`, p95 | ≤ 300 мс | 380 мс | 480 мс | **промах** |
| `POST /auth/otp/request`, p95 | ≤ 500 мс | 490 мс | 740 мс | **зависит от прогона** |
| `POST /auth/otp/verify`, p95 | ≤ 500 мс | 440 мс | 730 мс | **зависит от прогона** |
| `POST /rentals`, p95 | ≤ 1000 мс | 530 мс | 780 мс | выполнено |
| Открытие машины, p95 | ≤ 1000 мс | 1900 мс | 2800 мс | **промах** |
| Завершение аренды, p95 | ≤ 1000 мс | 2500 мс | 3400 мс | **промах** |
| Загрузка фото, p95 | ≤ 1500 мс | 1300 мс | 1700 мс | **зависит от прогона** |
| Задержка телеметрии, p95 | ≤ 2000 мс | 1200 мс | 1400 мс | выполнено |

**Вывод.** Пилот выдерживает нагрузку: весь парк в аренде, сбоев почти нет, все аренды оплачены. Но отвечает медленнее
целей. Открытие и завершение аренды не уложились в цель ни в одном из шести прогонов с этой нагрузкой, это главная
находка. Карта не уложилась в пяти из шести.

### Разброс между прогонами

На этом компьютере **одинаковый прогон может отличаться по p95 более чем вдвое**, поэтому одному прогону верить
нельзя. Все шесть прогонов с 50 машинами и 30 арендами:

| Показатель, p95 | 2 ноября, `e2560f9` | 3 ноября, `19bb5b1` | 3 ноября, итоговый код |
|---|---|---|---|
| `GET /map/cars` | 550 и 560 мс | 260 и 410 мс | 500 и 670 мс |
| Открытие машины | 2300 и 2500 мс | 1200 и 1600 мс | 1900 и 2800 мс |
| Завершение аренды | 2700 и 2500 мс | 1200 и 2500 мс | 2500 и 3400 мс |
| Загрузка фото | 1500 и 1500 мс | 820 и 1200 мс | 1300 и 1700 мс |

Четыре прогона 3 ноября шли подряд, между вторым и третьим были правки теста и дымовые прогоны, и почти все показатели
от прогона к прогону росли: карта 260, 410, 500, 670 мс. Итоговый код добавляет меньше 2% запросов, это
такой рост не объясняет. Похоже, что на скорость влияет состояние компьютера или Docker в длинной серии, но причину
мы не выясняли.

Чтобы сравнивать «до и после», нужно чередовать варианты в одной серии (A, B, A, B), а не снимать их друг за другом:
иначе рост внутри серии можно принять за эффект правки. Различие меньше двух раз без этого не доказано.

### Что видно в замере

- **API упирался в один процесс, база — нет.** Снимки `docker stats` раз в 30 с сделаны в одном прогоне 2 ноября, в
  остальных их не снимали. Процесс API занимал в среднем 91% ядра, пики до 167% (100% — одно ядро). В образе запущен
  один процесс uvicorn. Остальные не загружены: Postgres 8,5%, SeaweedFS 7%, Redis 1%, эмулятор 0,3%.
- **Хвост длинный.** Медиана карты 100–110 мс, а p95 — 500–670 мс. Похоже на ожидание в очереди процесса, но это
  гипотеза.
- **Единичные сбои.** В каждом прогоне 10–13 запросов карты и зон оборвались без ответа (`ConnectionError`), других
  сбоев нет. В одном прогоне 2 ноября открытие машины получило 504 `telematics-timeout`, аренда корректно отменилась.
  Причину этого 504 не разбирали.

### Что проверить при оптимизации

Это гипотезы по чтению кода, замером они не подтверждены. Каждую оптимизацию подтверждаем замером до и после.

1. **Перекодирование фото.** `clean_photo` (`core/photos.py`) декодирует и заново кодирует каждое фото с
   `optimize=True`. Это идёт в потоке, но в том же процессе, а фото приходят примерно 2,4 в секунду. Похоже на
   главного потребителя CPU.
2. **Запись телеметрии.** На каждую машину свой `UPDATE` в одной транзакции (`fleet/service.py`), всё это раз в 5 с
   и даже для стоящих машин. Транзакция держит блокировки строк машин, а бронь и команды пишут в те же строки.
   Возможная причина долгих p95 у открытия и завершения.
3. **Один процесс uvicorn.** Несколько процессов могут дать запас сразу, но поток парка рассылает сообщения изнутри
   процесса: сначала надо проверить, что это не сломает его ([ADR-0017](adr/0017-fleet-stream-websocket.md)).
4. **Пул соединений с БД.** Сейчас значения SQLAlchemy по умолчанию, настройки нет (`core/db.py`).
5. **Обрывы запросов карты.** Возможно, это гонка keep-alive: у uvicorn по умолчанию 5 с, а пауза клиента 5–15 с.

## Ограничения замера

- Генератор нагрузки делит компьютер со стеком, а между ними нет настоящей сети. На сервере абсолютные значения будут
  другими, а между прогонами они различаются более чем вдвое (см. «Разброс между прогонами»).
- Локально машины стоят на месте (`EMULATOR_SIMULATION_ENABLED=false`), иначе арендованная машина уезжает и не может
  завершить аренду. Телеметрия при этом идёт по расписанию, а тяжёлая часть сценария работает как обычно.
- **На стенде прогон ещё не запускался.** Это критерий #124 «запуск одной командой против стенда», он остаётся
  открытым. Юнит-тестами покрыты только план стенда, отмена брони при уехавшей машине и вход без подмены адреса.
  Настоящие движущиеся машины, один токен на два сокета и лимиты стенда ничем не проверены.
- В логах прогонов простой поиск не нашёл токенов и телефонов. Это не заменяет проверку логов из чек-листа
  безопасности, которая остаётся в #124.
