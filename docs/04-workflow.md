# 04. Рабочий процесс команды

Команда работает **асинхронно**, без жёсткого деления зон: любой может взять любую задачу.
Чтобы это не превратилось в хаос, всё держится на трёх вещах: **задачи в GitHub**, **PR с ревью**,
**общие правила для Claude Code**.

## Инструменты

| Что | Где |
|---|---|
| Код | GitHub, приватный репозиторий организации (GitHub Student / Team) |
| Задачи и план | GitHub Projects (доска: Backlog → Ready → In progress → Review → Done) |
| Решения по архитектуре | `docs/adr/` (ADR — короткая запись «что решили и почему») |
| Обсуждения | GitHub Discussions или комментарии в задаче. Важное из мессенджера переносится в задачу |
| CI | GitHub Actions |
| AI | Claude Code у каждого, общие правила в `CLAUDE.md` и `.claude/` |

## Жизненный цикл задачи

1. **Задача создаётся в GitHub Issues** по шаблону (feature / bug). В ней: что и зачем, критерии приёмки.
   Большие фичи режутся на задачи по 0.5–2 дня.
2. **Берёшь задачу** — назначь себя и перенеси в *In progress*. Одна задача — один человек — одна ветка.
3. **Ветка** от `main`: `feat/123-short-name`, `fix/123-...`, `chore/...`, `docs/...` (123 — номер задачи).
4. **Работа с Claude Code** — см. раздел ниже.
5. **PR** в `main` по шаблону. Маленький (до ~400 строк изменений без сгенерированного кода).
   В описании `Closes #123`.
6. **CI зелёный** — обязательное условие.
7. **Ревью вторым человеком** — обязательно. Ревьюер отвечает в течение 1 рабочего дня.
   Для чувствительных модулей дополнительно `/security-review` (см. [03-security](03-security.md)).
8. **Squash merge** в `main`. Ветка удаляется.

`main` защищена: прямой push запрещён, нужен 1 approve и зелёный CI.

## Коммиты

[Conventional Commits](https://www.conventionalcommits.org/ru/) на английском:

```
feat(rentals): add reservation timeout job
fix(identity): reject reused refresh tokens
docs(adr): record maps decision
```

Типы: `feat`, `fix`, `refactor`, `test`, `docs`, `chore`, `ci`, `perf`, `security`.
Scope — модуль или приложение (`api`, `mobile`, `admin`, `emulator`, `rentals` …).

## Definition of Done

Задача считается сделанной, когда:
- [ ] Критерии приёмки из задачи выполнены
- [ ] Есть тесты на новую логику (бэкенд — обязательно; фронт — на нетривиальную логику)
- [ ] Линтеры, типы, тесты проходят в CI
- [ ] Строки интерфейса — через i18n (ru + en)
- [ ] Если поменялся API — перегенерирован `packages/api-client`
- [ ] Если принято архитектурное решение — добавлен ADR
- [ ] Если поменялся способ запуска/настройки — обновлена документация
- [ ] Ревью пройдено

## Как работать с Claude Code

### Общие принципы
- **Человек отвечает за код, а не AI.** Ты мержишь только то, что понимаешь. Непонятное — попроси Claude объяснить
  или упростить.
- **`CLAUDE.md` и `.claude/settings.json` — общие** и лежат в репозитории. Меняются через PR, как код.
  Личные настройки — в `.claude/settings.local.json` (не коммитится).
- **Одна задача — одна сессия Claude Code.** Начинай сессию со ссылки на задачу: «Сделай #123».
- Для параллельной работы над несколькими задачами — отдельные **worktree** (в десктоп-приложении
  Claude Code это включается при создании сессии), чтобы изменения не смешивались.

### Общие команды проекта

Лежат в `.claude/skills/`, одинаковы у всех. Вызываются в чате Claude Code через `/`:

| Команда | Что делает |
|---|---|
| `/start-task 123` | Читает задачу, назначает тебя, создаёт ветку от свежего `main`, собирает контекст, предлагает план |
| `/ship` | Прогоняет проверки, самоаудит, коммит, push, PR по шаблону с запросом ревью |
| `/review-pr 45` | Готовит ревью PR коллеги: must fix / should fix / nit. Публикует только по твоей команде |
| `/new-adr` | Оформляет архитектурное решение в `docs/adr/` |
| `/weekly-update` | Собирает еженедельный апдейт из активности на GitHub |
| `/code-review`, `/simplify`, `/security-review` | Встроенные проверки Claude Code перед PR |

Новые общие команды добавляются через PR в `.claude/skills/<имя>/SKILL.md`.

### Рекомендуемый цикл
1. **План.** Для всего крупнее мелкой правки — режим планирования (plan mode): Claude изучает код и
   предлагает план, ты правишь план до начала кодинга. Это дешевле, чем переделывать код.
2. **Реализация + тесты.** Попроси сначала тесты на критерии приёмки, потом код.
3. **Самопроверка.** Перед PR: `/code-review` (ищет ошибки) и `/simplify` (убирает лишнее);
   для чувствительных модулей — `/security-review`.
4. **PR.** Claude создаёт PR по шаблону; ты перечитываешь diff целиком.
5. **Ревью коллеги.** Коллега может проверять PR со своим Claude Code, но approve ставит человек.

### Чего не делать
- Не просить «сделай весь модуль оплаты» одним запросом — режь на задачи.
- Не мержить код, где Claude «временно» отключил проверку, тест или линтер.
- Не вставлять в чат с AI реальные персональные данные и боевые секреты.
- Не править `CLAUDE.md` «под себя» без PR — он общий.

## Асинхронная синхронизация

- **Еженедельный апдейт** (понедельник): короткий пост в Discussions — что сделано, что дальше, где нужна помощь.
- **Итерации по 2 недели.** В начале итерации — выбор задач из бэклога (письменно в Discussions или
  короткий созвон по желанию). В конце — демо-видео/скриншоты в Discussions.
- **Блокеры** — сразу в задаче с упоминанием коллеги, не ждать апдейта.

## Рост команды

Процесс изначально рассчитан на расширение:
- Новый человек проходит [онбординг](06-onboarding.md) и берёт задачу с меткой `good first issue`.
- При 4+ разработчиках — появляются владельцы модулей (`CODEOWNERS`) и обязательное ревью владельца.
- При появлении отдельных ролей (дизайнер, QA, DevOps) — их зоны описываются здесь же.
- Все договорённости живут в репозитории, а не в головах и чатах.
