# 04. Рабочий процесс команды

Команда работает **асинхронно**, без жёсткого деления зон: любой может взять любую задачу.
Чтобы это не превратилось в хаос, всё держится на трёх вещах: **задачи в GitHub**, **PR с ревью**,
**общие правила для Claude Code**.

## Инструменты

| Что | Где |
|---|---|
| Код | GitHub, приватный репозиторий организации (GitHub Student / Team) |
| Задачи и план | GitHub Projects (доска: Backlog → Ready → In progress → Review → Done) |
| Решения по архитектуре | `docs/adr/` (ADR — короткая запись «что решили и почему») |
| Обсуждения | GitHub Discussions или комментарии в задаче. Важное из мессенджера переносится в задачу |
| CI | GitHub Actions |
| AI | Claude Code у каждого, общие правила в `CLAUDE.md` и `.claude/` |

## Жизненный цикл задачи

1. **Задача создаётся в GitHub Issues** по шаблону (feature / bug). В ней: что и зачем, критерии приёмки.
   Большие фичи режутся на задачи по 0.5–2 дня.
2. **Берёшь задачу** — `/start-task <номер>` назначает тебя и переносит задачу в *In progress*.
   Одна задача — один человек — одна ветка.
3. **Ветка** от `main`: `feat/123-short-name`, `fix/123-...`, `chore/...`, `docs/...` (123 — номер задачи).
4. **Работа с Claude Code** — см. раздел ниже.
5. **PR** в `main` по шаблону. Маленький (до ~400 строк изменений без сгенерированного кода).
   В описании `Closes #123`.
6. **CI зелёный** — обязательное условие.
7. **Ревью вторым человеком** — обязательно. Ревьюер отвечает в течение 1 рабочего дня.
   Для чувствительных модулей дополнительно `/security-review` (см. [03-security](03-security.md)).
8. **Squash merge** в `main`. `/ship` включает автослияние: PR сливается сам, как только есть approve
   и CI зелёный. Ветка удаляется, задача закрывается через `Closes #123`.

`main` защищена: прямой push запрещён, нужен 1 approve и зелёный CI.

### Что проверяет CI

Workflow `.github/workflows/ci.yml` запускается на каждый PR и push в `main`:

| Часть | Проверки |
|---|---|
| `apps/api`, `services/car-emulator` | `ruff check`, `ruff format --check`, `mypy`, `lint-imports` (только api), `pytest` (Postgres/Redis через testcontainers), `pip-audit` |
| npm workspaces: `apps/mobile`, `apps/admin`, `packages/*` | из корня: `npm ci`, `npm run lint`, `npm run typecheck`, `npm test`, `check:deps` и `check:bundle` (мобилка), `npm run audit` |
| `packages/api-client` | сгенерированный клиент актуален: `npm run gen:api` не меняет файлы |
| весь репозиторий | Semgrep (SAST), gitleaks и проверка заголовка PR (`repo-checks.yml`) |

- Проверяются только изменённые части; части, которых ещё нет в репозитории, пропускаются.
  Правка самого `ci.yml` запускает все проверки.
- В `package.json` каждой JS-части обязательны скрипты `lint`, `typecheck`, `test`.
- Обязательный для `main` статус — `CI gate`: он есть всегда и зелёный, если все запущенные проверки прошли.
  Список обязательных проверок задаётся в `scripts/setup-github.ps1`.

## Коммиты

[Conventional Commits](https://www.conventionalcommits.org/ru/) на английском:

```
feat(rentals): add reservation timeout job
fix(identity): reject reused refresh tokens
docs(adr): record maps decision
```

Типы: `feat`, `fix`, `refactor`, `test`, `docs`, `chore`, `ci`, `perf`, `security`.
Scope — модуль или приложение (`api`, `mobile`, `admin`, `emulator`, `rentals` …).

## Definition of Done

Задача считается сделанной, когда:
- [ ] Критерии приёмки из задачи выполнены
- [ ] Есть тесты на новую логику (бэкенд — обязательно; фронт — на нетривиальную логику)
- [ ] Линтеры, типы, тесты проходят в CI
- [ ] Строки интерфейса — через i18n (ru + en)
- [ ] Если поменялся API — перегенерирован `packages/api-client`
- [ ] Если принято архитектурное решение — добавлен ADR
- [ ] Если поменялся способ запуска/настройки — обновлена документация
- [ ] Ревью пройдено

## Как работать с Claude Code

### Общие принципы
- **Человек отвечает за код, а не AI.** Ты мержишь только то, что понимаешь. Непонятное — попроси Claude объяснить
  или упростить.
- **`CLAUDE.md` и `.claude/settings.json` — общие** и лежат в репозитории. Меняются через PR, как код.
  Личные настройки — в `.claude/settings.local.json` (не коммитится).
- **Одна задача — одна сессия Claude Code.** Начинай сессию со ссылки на задачу: «Сделай #123».
- Для параллельной работы над несколькими задачами — отдельные **worktree** (в десктоп-приложении
  Claude Code это включается при создании сессии), чтобы изменения не смешивались.

### Настройка десктоп-приложения Claude (вкладка Code)

- **Папка проекта.** Все сессии создаются в папке репозитория. В боковой панели они собираются
  в один раздел с именем папки (группировка «по проекту»).
- **Сессия-«штаб».** Одна закреплённая (Pinned) сессия на проект — для вопросов по организации,
  процессу и документации. Код в ней не пишется.
- **Задача = новая сессия с worktree.** «Новое» → папка проекта → включить worktree → `/start-task <номер>`.
  Worktree создаются в `.claude/worktrees/` (папка в `.gitignore`), у каждой сессии своя ветка,
  поэтому несколько задач можно вести параллельно.
- **Автоархив.** В Settings → Claude Code включите «Auto-archive sessions when their pull request closes»:
  после слияния PR сессия задачи сама уходит в архив и не засоряет список.
- **Имена сессий.** Называйте сессию по задаче: `#12 вход по OTP`. Так её легко найти поиском.
- **PR в приложении.** После `/ship` приложение само показывает статус CI и ревью PR в сессии.
- Раздел «Проекты (бета)» в левом меню относится к чатам claude.ai, для работы с кодом он не нужен.

### Общие команды проекта

Лежат в `.claude/skills/`, одинаковы у всех. Вызываются в чате Claude Code через `/`:

| Команда | Что делает |
|---|---|
| `/start-task 123` | Читает задачу, назначает тебя, переводит её в *In progress*, готовит ветку от свежего `main`, собирает контекст, предлагает план и публикует его в задаче |
| `/ship` | Подтягивает свежий `main`, прогоняет проверки, самоаудит, коммит, push, PR по шаблону с ревьюерами (все остальные участники), метками и автослиянием, переводит задачу в *Review* |
| `/pick-task` | Ищет свободную задачу, которая не пересекается с открытыми PR и задачами коллег в работе, и предлагает взять её через `/start-task` |
| `/pre-ship-review` | Перед `/ship`: субагент без контекста сессии читает diff ветки как придирчивый коллега (с учётом того, к чему команда цепляется на ревью) и выдаёт must fix / should fix / nit; исправляет выбранное |
| `/review-pr 45` | Готовит ревью PR коллеги: must fix / should fix / nit. Публикует только по твоей команде. Без номера — показывает PR, где ты ревьюер |
| `/review-open-prs` | Проходит все открытые PR коллег: ревьюит новые и обновлённые, отвечает авторам в ветках обсуждений, апрувит то, что в порядке. Изменения в identity, kyc, payments, rentals и командах машинам без security review не апрувит |
| `/project-status` | Статус проекта: прогресс этапа, кто что делает, PR и CI, что делать дальше. Заодно чинит колонки на доске |
| `/sync` | Подтягивает свежий `main` в текущую ветку, разрешает конфликты, прогоняет проверки |
| `/demo` | Собирает и запускает текущую версию: админку и клиентское приложение во встроенном браузере (`/demo phone` — в Expo Go на телефоне, `/demo api` — ещё бэкенд и эмулятор в Docker), проводит короткую экскурсию |
| `/new-adr` | Оформляет архитектурное решение в `docs/adr/` |
| `/weekly-update` | Собирает еженедельный апдейт из активности на GitHub |
| `/code-review`, `/simplify`, `/security-review` | Встроенные проверки Claude Code перед PR |

Новые общие команды добавляются через PR в `.claude/skills/<имя>/SKILL.md`.

### Что происходит автоматически

| Событие | Что делается само | Кем |
|---|---|---|
| `/start-task` | Задача назначена на тебя, на доске *In progress*, план в комментарии к задаче | Claude Code |
| `/ship` | Ревьюеры (все, кроме автора), метки `area:*`, автор в assignees, на доске *Review*, автослияние | Claude Code |
| Approve + зелёный CI | PR сливается squash-ом, ветка удаляется, задача закрывается | GitHub |
| Задача закрыта | На доске *Done* | GitHub Projects (встроенная автоматизация, см. ниже) |
| PR отстал от `main` | Кнопка «Update branch» на странице PR или `/sync` | GitHub / Claude Code |
| Сессия задачи после слияния PR | Уходит в архив | Приложение Claude (настройка автоархива) |
| `/project-status` | Расхождения на доске исправляются | Claude Code |

Доска перемещает задачи в *Done* сама только при включённой встроенной автоматизации:
Project → ⋯ → Workflows → включить **Item closed** (→ Done) и **Pull request merged** (→ Done).
Включается один раз владельцем доски. Перемещение задач между колонками делает скрипт
`scripts/board-status.sh`, его вызывают команды `/start-task`, `/ship`, `/project-status`.

Автослияние можно выключить на странице PR (кнопка «Disable auto-merge») или командой `gh pr merge --disable-auto`,
если хочется слить вручную.

### Рекомендуемый цикл
1. **План.** Для всего крупнее мелкой правки — режим планирования (plan mode): Claude изучает код и
   предлагает план, ты правишь план до начала кодинга. Это дешевле, чем переделывать код.
2. **Реализация + тесты.** Попроси сначала тесты на критерии приёмки, потом код.
3. **Самопроверка.** Перед PR: `/code-review` (ищет ошибки) и `/simplify` (убирает лишнее);
   для чувствительных модулей — `/security-review`.
4. **PR.** Claude создаёт PR по шаблону; ты перечитываешь diff целиком.
5. **Ревью коллеги.** Коллега может проверять PR со своим Claude Code, но approve ставит человек.

### Чего не делать
- Не просить «сделай весь модуль оплаты» одним запросом — режь на задачи.
- Не мержить код, где Claude «временно» отключил проверку, тест или линтер.
- Не вставлять в чат с AI реальные персональные данные и боевые секреты.
- Не править `CLAUDE.md` «под себя» без PR — он общий.

## Асинхронная синхронизация

- **Еженедельный апдейт** (понедельник): короткий пост в Discussions — что сделано, что дальше, где нужна помощь.
- **Итерации по 2 недели.** В начале итерации — выбор задач из бэклога (письменно в Discussions или
  короткий созвон по желанию). В конце — демо-видео/скриншоты в Discussions.
- **Блокеры** — сразу в задаче с упоминанием коллеги, не ждать апдейта.

## Рост команды

Процесс изначально рассчитан на расширение:
- Новый человек проходит [онбординг](06-onboarding.md) и берёт задачу с меткой `good first issue`.
- При 4+ разработчиках — появляются владельцы модулей (`CODEOWNERS`) и обязательное ревью владельца.
- При появлении отдельных ролей (дизайнер, QA, DevOps) — их зоны описываются здесь же.
- Все договорённости живут в репозитории, а не в головах и чатах.
