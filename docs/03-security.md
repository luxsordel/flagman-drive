# 03. Безопасность

Ориентир — **OWASP ASVS уровень 2** для бэкенда и веба, **OWASP MASVS** для мобильного приложения.
Каршеринг — это деньги, персональные данные и физический доступ к машине, поэтому безопасность
закладывается с первого коммита, а не «потом».

## Что защищаем

| Актив | Угроза | Последствие |
|---|---|---|
| Команды машине (открыть/завести) | Чужой человек открывает машину | Угон |
| Документы клиентов (паспорт, права, селфи) | Утечка | Ущерб людям, ответственность по закону о ПД |
| Платёжные операции | Списания/возвраты без права | Потеря денег |
| Аккаунты сотрудников | Захват админки | Всё вышеперечисленное |
| Расчёт стоимости поездки | Подмена клиентом | Бесплатные поездки |

## Обязательные правила

### Аутентификация и сессии
- Клиенты: телефон + OTP (6 цифр, живёт 5 мин, ≤ 5 попыток, лимиты на номер и IP — защита от SMS-флуда).
  - Исключение на время пилота, пока нет SMS-шлюза (`SMS_BACKEND=fixed`, [ADR-0009](adr/0009-client-auth-jwt-and-sessions.md)):
    входят только заранее заведённые тестовые номера, у всех один код. Код случайный (легко угадываемые
    отклоняются), не отправляется и не пишется в лог; попытки и лимиты те же. С реальными клиентами не использовать.
    Так входят и на демо-стенд (`API_ENV=stand`, [docs/08-demo-stand.md](08-demo-stand.md)): защиты там как в
    проде, но разрешены тестовые платежи и демо-данные.
- Сотрудники: email + пароль (argon2id) + **обязательная 2FA (TOTP)**.
- Access-токен (JWT) — 15 минут; refresh-токен — ротация при каждом обновлении, в БД хранится только хэш;
  повторное использование старого refresh в живой сессии → отзыв всех сессий этого устройства; в закончившейся
  сессии → 401 без отзыва, чтобы старой копией нельзя было выкидывать владельца с устройства. Исключение —
  первые 30 секунд после ротации (`REFRESH_REUSE_GRACE`): такой повтор получает 401 `refresh-token-invalid`
  без отзыва (в логе — `refresh_token_already_rotated`), чтобы одновременные обновления из соседних вкладок не выкидывали пользователя ([ADR-0009](adr/0009-client-auth-jwt-and-sessions.md)).
- Мобильные: токены только в `expo-secure-store` (Keychain / Keystore). Веб: refresh — в
  `HttpOnly; Secure; SameSite=Strict` cookie, access — только в памяти.

### Авторизация
- Проверка прав на **каждом** эндпоинте и на уровне объекта: клиент видит только свои аренды,
  документы, платежи (защита от IDOR). Делается общими зависимостями FastAPI, а не ручными `if` в роутерах.
- Внешние идентификаторы — UUID, а не последовательные числа.
- Команда «открыть машину» разрешена, только если у клиента активная аренда **этой** машины, KYC одобрен,
  клиент не заблокирован и геопозиция ≤ 50 м от машины. Всё проверяет **сервер**.
  Клиенту, заблокированному во время поездки, разрешено только закрыть машину (ADR-0026).

### Деньги и бизнес-логика
- Стоимость считает только сервер. Клиент никогда не присылает цены, тарифы и суммы.
- Платёжные операции идемпотентны (`Idempotency-Key`); вебхуки платёжки — с проверкой подписи.
- Корректировки сумм сотрудниками — только с комментарием и записью в аудит. Чек не меняется: корректировка —
  отдельная строка, уменьшение возвращает деньги через `payments`, увеличение становится долгом (ADR-0026).
- Принудительное завершение аренды и блокировка клиента — только `operator` и `admin`, с обязательной причиной
  и записью в аудит. Причины хранятся вне журнала аудита (`rentals.force_finish_reason`, `client_block_events`),
  в аудите — только id (ADR-0026).

### Данные
- Все входные данные валидируются Pydantic-схемами, лишние поля запрещены (`extra="forbid"`). Правило касается
  тел запросов и query-моделей (вместе с вложенными); это проверяет
  `tests/test_input_schemas.py::test_every_input_model_forbids_unknown_fields`.
- SQL — только через SQLAlchemy с параметрами. Сборка SQL из строк запрещена.
- Фото документов — приватный бакет, доступ по подписанным ссылкам (≤ 5 минут), только владельцу и
  операторам KYC. Проверка типа файла по содержимому, лимит размера, удаление EXIF. Фото и ссылки на них
  не кэшируются (`Cache-Control: no-store`, ADR-0012).
- Фото в чате поддержки и в инцидентах хранятся так же. Доступ — только владельцу и операторам поддержки
  (`operator`, `admin`), каждая ссылка сотруднику фиксируется в журнале аудита (ADR-0023).
- Фото осмотров аренды сотрудникам выдаются так же: короткоживущие ссылки, каждая — в журнал аудита (ADR-0026).
- Фото задач техникам хранятся так же: они снимают те же машины и повреждения. Каждая ссылка
  фиксируется в журнале аудита (ADR-0025).
- Фото-доказательства штрафов хранятся так же. Их видят клиент, которому начислен штраф, и `operator`,
  `admin`. Каждая ссылка сотруднику фиксируется в журнале аудита (`fine.photo_viewed`). Загрузку
  ограничивает лимит частоты (ADR-0028).
- Персональные данные не пишутся в логи (маскирование телефонов, токенов, номеров документов). Пишем только id;
  страховка от промаха — общий процессор в `core/logging.py`, который заменяет на `[redacted]` значения полей
  из явного списка (телефон, email, ФИО, дата рождения, координаты, IP, пароли, токены, номер документа
  и т. п.). Query-строка в строке WebSocket-рукопожатия uvicorn отрезается, как и в access-логе.
- Минимизация: храним только нужное; сроки хранения документов определить с юристом.

### Транспорт и заголовки
- Только HTTPS (HSTS). CORS — явный список доменов. Заголовки безопасности: CSP для админки,
  `X-Content-Type-Options`, `Referrer-Policy`, `frame-ancestors 'none'`.
- Rate limiting на чувствительных эндпоинтах: вход, OTP, команды машине, платежи, сообщения в
  поддержку, загрузка фото и сообщения об инцидентах.
- Вебхуки телематики и платёжки — подпись HMAC + метка времени (защита от повтора).

### Секреты
- Секреты **никогда** не коммитятся. Локально — `.env` (в `.gitignore`), шаблон — `.env.example` без значений.
- В облаке — секреты GitHub Actions / менеджер секретов хостинга.
- В CI — сканер утечек секретов (gitleaks).

### Зависимости и CI
- Dependabot для pip, npm, GitHub Actions, Dockerfile-образов и сторонних образов docker-compose
  (`infra/docker-compose.yml`, `infra/stand/compose.yml`). Мажорные версии Postgres и Redis обновляются вручную.
- Dependabot alerts и security updates включены в настройках репозитория (включает администратор).
- В CI: `pip-audit`, `npm audit` (high и critical, `scripts/npm-audit.mjs`), **Semgrep** (SAST), **gitleaks**.
  Первые три живут в `.github/workflows/dependency-scans.yml`: его вызывает `ci.yml` на PR и `scheduled-scans.yml`
  по понедельникам в 04:00 UTC по всему `main`, чтобы новая уязвимость в нетронутой зависимости не ждала следующего PR.
  Упавший плановый скан открывает issue «Weekly dependency scan failed» с меткой `security` (или пишет в уже открытую),
  следующий успешный — закрывает её. Вручную: Actions → scheduled-scans → Run workflow.
- Исключение из `npm audit` — только когда исправленной версии нет: запись в `.github/npm-audit-allowlist.json`
  с идентификатором GHSA, причиной (почему не эксплуатируется у нас) и датой `reviewBy` (не дальше 3 месяцев).
  После этой даты CI снова падает. Запись, которую `npm audit` больше не сообщает, тоже роняет CI: её надо удалить.
  В описании PR с исключением — отдельный пункт для ревьюера.
- Зафиксированные версии: `uv.lock`, `package-lock.json`.

### Мобильное приложение
- Никаких секретов в коде приложения — всё, что в бандле, считается публичным.
- Certificate pinning и обнаружение root/jailbreak — перед боевым запуском.

### Аудит и мониторинг
- Журнал аудита (только вставка, без изменения/удаления): действия сотрудников, команды машинам, денежные операции.
  Команда, которую машина уже получила, остаётся в журнале и при сбое записи после отправки: событие пишется
  отдельной транзакцией, а при недоступной БД остаётся `error` `car_command_audit_failed` с `command_id` (ADR-0030).
- Алерты на аномалии: всплеск неудачных входов, массовые команды машинам. В пилоте это `warning`
  `security_spike` в логе API, когда общий по всем пользователям счётчик доходит до порога: неудачные
  входы клиентов 20 за 5 мин, сотрудников 8 за 5 мин, команды машинам от сотрудников 40 за 5 мин, от
  клиентов 120 в минуту (ADR-0029). Без ПД; сбой счётчика всплесков (Redis) не превращает в 500 отказ во входе
  или команду, уже выполненную машиной. Лимитер запросов при этом тоже в Redis, и без Redis вход и команды
  не работают. Внешние оповещения — перед боевым запуском.

## Перед боевым запуском (вне пилота)

- [ ] Внешний пентест (API, мобильное приложение, админка).
- [ ] Юридическая проверка обработки ПД по Закону РБ № 99-З «О защите персональных данных»:
      место хранения, трансграничная передача, согласия, политика конфиденциальности.
- [ ] Модель угроз для реальной телематики (защита канала до блока в машине).
- [ ] План реагирования на инциденты.
- [ ] Certificate pinning и обнаружение root/jailbreak в мобильном приложении.
- [ ] Настоящий SMS-шлюз вместо `SMS_BACKEND=fixed`. Сейчас конфигурация не запрещает `fixed` в проде,
      запрет надо добавить вместе со шлюзом.
- [ ] Сроки хранения фото (документы, поддержка, инциденты, осмотры, задачи, штрафы) и журнала аудита —
      после консультации с юристом, и задача удаления по этим срокам.
- [ ] Внешние оповещения об аномалиях (сейчас только `security_spike` в логе API).

## Как AI помогает с безопасностью

- PR, затрагивающие `identity`, `kyc`, `payments`, `rentals` или команды машине, проходят
  `/security-review` в Claude Code **и** ревью человеком.
- Краткая выжимка этих правил есть в [CLAUDE.md](../CLAUDE.md), чтобы ассистент соблюдал их при генерации кода.
